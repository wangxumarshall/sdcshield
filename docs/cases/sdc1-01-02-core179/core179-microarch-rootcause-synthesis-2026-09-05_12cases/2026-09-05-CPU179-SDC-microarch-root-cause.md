# CPU179 静默数据损坏（SDC）微架构根因研究报告
## 12 次 vmcore 原始转储的独立取证与芯片设计启示

> 研究方法：本文档完全基于 `/home/sdc/wangxu/vmcore0102/127.0.0.1-*/` 下 12 份原始
> vmcore 转储与其 dmesg 日志独立取证（crash 8.0.4 + vmlinux 调试符号），未参考任何
> 既有分析文档。所有结论均可由原始证据复核。

## 1. 执行摘要

一台 192 核（2 路鲲鹏类 ARMv8.2，Yangtze Computing R240K V2，805GB DDR，
openEuler 24.03 SP3，内核 6.6.0-145.3.23.154）服务器在 22 天内产生 12 次
kdump 转储。取证结论：

全部 135 次警告级故障与 12 次致命 Oops 100% 发生在同一个物理核 CPU179
（MPIDR 0x817a0300，socket1 / cluster 0x7a / core3）。根因是该核私有存储子系统
（L1D cache / TLB / page-walk cache 一类核内 SRAM）存在固定硬件缺陷：
LOAD 指令偶发读出"错误的 64 位数据"，两种形态：读回写入前的旧值（stale，
实测读出精确的 0），或读出散布 2~7 位翻转的乱数据。该通路无 ECC/parity
保护，ARM64 核心 RAS 错误记录寄存器零锁存，错误以 SDC 形式直接进入软件
数据结构，最终污染指针引发致命翻译故障。

一句话：CPU179 这个核的"芯内私有 SRAM 读出路径"坏了，而且坏得悄无声息，芯片没有任何报错。

## 2. 证据链

### 2.1 单点定域：全部故障锁定 CPU179

| 统计项 | 数值 | 说明 |
|---|---|---|
| 转储数 | 12 | 2026-08-14 ~ 09-04，跨度 22 天，12 次独立启动（KASLR 基址各不相同） |
| spurious fault 警告 | 135 次 | **全部 CPU179**（逐一核验：非 179 的 WARNING 为 0 条） |
| 致命 Oops | 12 次 | **全部 CPU179** |
| 随机概率 | (1/192)^147 ≈ 10^-334 | 若故障随机分布到核上，全落一个核的概率为零 |

12 次启动 KASLR 各异（&runqueues 分别为 ffffa5aa…、ffffd770… 等不同值），
排除了特定虚拟地址布局的软件触发因素。故障时间从开机 418 秒到 537462 秒
不等，最早 835 秒即出现症状，缺陷从启动早期就活跃。

### 2.2 致命 Oops 的解剖：一条指令的取证

12 次致命 Oops 中 11 次发生在同一处：`find_busiest_group+0x140`（调度器负载
均衡读 per-cpu 统计的热路径）。反汇编（vmlinux 符号验证）：

```asm
find_busiest_group+296: ldp  x0, x1, [sp, #8]        // x0=&__per_cpu_offset, x1=&runqueues
find_busiest_group+308: ldr  x20, [x0, w25, sxtw #3] // x20 = __per_cpu_offset[cpu]
find_busiest_group+316: add  x27, x1, x20            // x27 = &runqueues + per_cpu_offset[cpu]
find_busiest_group+320: ldr  x23, [x27, #288]        // ★ 故障指令（Code dump: f9409377）
```

正常的 per-cpu 寻址。判定性的算术：

- `&runqueues`（per-cpu 模板符号）低 12 位恒为 **0x6c0**（KASLR 2MB 对齐 + 段内偏移 0x176c0，与启动基址无关）
- `__per_cpu_offset[cpu]` 低 12 位恒为 **0x000**（per-cpu chunk 对齐）
- 因此正常的 x27 低 12 位必须等于 **0x6c0**

实测 12 次崩溃的 x27 分两族：

族 B（5 例），x20 读出精确的 0（stale 旧值）：

| 转储 | x27（崩溃现场） | 各自启动的 &runqueues（crash 符号表） |
|---|---|---|
| 08-25-15:42 | ffffa5aa9b5a96c0 | ffffa5aa9b5a96c0（**精确相等**） |
| 08-26 | ffffa29301d796c0 | ffffa29301d796c0（精确相等） |
| 09-04-10:27 | ffffd99f13ae96c0 | （低 12 位 0x6c0 ✓） |
| 09-04-11:00 | ffffd77069c696c0 | ffffd77069c696c0（精确相等） |
| 09-04-12:33 | ffffc8a996d396c0 | （低 12 位 0x6c0 ✓） |

x20 读出 0 → x27 = &runqueues（静态模板地址而非任何 CPU 的实际副本）→
`ldr [x27+0x120]` 落在内核镜像 .data..percpu 模板段的 PMD 空洞（实测 vtop：
该 2MB PMD 条目为 0，而相邻内核代码段 PMD 正常）→ L2/L3 translation
fault → Oops。`__per_cpu_offset[]` 是 boot 期写入、运行期只读的数组；读出
精确 0 = 读到了它被写入之前的初始值。这是缓存一致性失效/stale 行的教科书式
指纹。转储中该数组数据完好（ffffa89016xxxxx，单调正确）。内存没坏，坏的是"读出"环节。

族 A（6 例），x20 读出散布多位翻转的乱数据：

| 转储 | x27 | 低12位 vs 0x6c0 的 XOR | 错误位数 | 高16位本应 ffff |
|---|---|---|---|---|
| 08-14 | d936bc836a4a96bf | 0x07f | 7 | 实为 d936 |
| 08-17 | 00ffd780f5a3a6a0 | 0x060 | 2 | 实为 00ff |
| 08-25-15:58 | 00ffb34569fc39a0 | 0xf60 | 6 | 实为 00ff |
| 08-31 | a000c1a9443c91e5 | 0x725 | 6 | 实为 a000 |
| 09-03 | 00ffc99ebbaad000 | 0x6c0 | 4 | 实为 00ff |
| 09-04-09:15 | 2cd7ddf3a9089670 | 0x0b0 | 3 | 实为 2cd7 |

同一个 64 位字内，高位与低位同时出现 2~7 位散布错误。这不是单粒子翻转
（典型 1~2 位），而是同一 SRAM 字内多个弱单元同时读错的缺陷指纹。

**转储 3（08-24）旁证**：唯一非调度器崩溃，writeback 路径 `bio_add_page+0xf0`，
x3=0x553c521da2e9b99f，且 x24=ffff404420819b68（线性映射地址但物理超过
4.4TB，远超 805GB 内存 = 无效指针）。不同受害结构，同一 CPU179，同一根因。

### 2.3 135 次 spurious fault：第三种形态

```c
Ignoring spurious kernel translation fault at virtual address ffff6040...
WARNING: CPU: 179 ... __do_kernel_fault
```

- 触发路径 100% 一致：读 /proc/interrupts（irqbalance/pmdalinux 周期执行）→
  `show_interrupts → seq_printf → __memcpy` 中触发 translation fault
- ESR=0x96000044：**level 0** translation fault，触发对象是一个完全合法的内核地址
- 内核重走页表发现映射完好，判定"虚假故障"并忽略。重走即成功。

硬件页表走查瞬时得到错误结果、软件重走立即正确：故障出在 walk 路径的缓存
状态（TLB / page-walk cache / L1 中的页表行），与页表内存本身无关。这是与
2.2 节相同的 stale/corrupt 机理在翻译子系统上的表现。

### 2.4 芯片报错缺席：RAS 记录为零

转储 6 中 8026 秒处有 rasnode 模块扫描全部 CPU 的 ARM64 标准错误记录节点
（每核 ERRIDR=4，5 个 ERR 节点）：

```
rasnode: cpu=179 node=0 FR=0000000000004842 CTLR=0000000000000101 STATUS=00000000000000ff ...
rasnode: cpu=179 node=1 FR=00000000000249a2 CTLR=0000000000000505 STATUS=00000000000000ff ...
```

CPU179 的全部节点与系统其他 191 个核**完全一致**（均为复位默认值），
错误发生时没有任何检测电路报警。同时 12 份日志中零 EDAC/CE/UE 记录。
这说明出错的数据通路（核私有 cache/TLB SRAM 读出路径）不在 ECC/parity
保护范围内。

### 2.5 排除法

| 假设 | 排除依据 |
|---|---|
| 软件 bug | 12 次独立启动 KASLR 各异而模式一致；x27 精确等于 &runqueues（巧合概率为零）；转储中数据完好 |
| DDR/内存条故障 | 若 DDR 坏：故障应跨核随机分布；重走页表不会成功；转储中相关数据（__per_cpu_offset[]、页表）完好 |
| LLC（共享 L3）故障 | L3 为簇间共享，故障应出现在多个核；且 805GB 服务器 L3 通常有 ECC 保护并会留 RAS 记录 |
| 宇宙射线单粒子翻转 | 22 天稳定锁定同一核、错误位散布 2~7 位、时域从开机 418s 持续到 537462s；这是永久性缺陷，不是瞬态事件 |
| 温度/电压瞬态 | 无任何 thermal/throttle 事件；频率恒定复现跨度 22 天 |

### 2.6 物理定位

CPU179 = MPIDR 0x817a0300：socket 1，cluster 0x7a（含 CPU176-179），core 3。
boot 日志（掩码后 0x7a0300）与 rasnode（全值 0x817a0300）互相印证。

## 3. 微架构根因模型

```
CPU179 核内私有 SRAM（L1D 阵列 / TLB 阵列 / page-walk cache 之一或若干）
存在固定制造/设计缺陷
        │
        ├─ 形态1: 读出 stale 值（写入前的旧数据） ──────→ 族B（5例致命）+ 一部分spurious
        │    实测: __per_cpu_offset[cpu] 读出精确 0（初始值）
        │    机理候选: 位线/灵敏放大器时序裕量不足、写穿透失败、
        │             cache 行替换/更新路径的时序违例
        │
        ├─ 形态2: 读出散布多位错误（2~7bit/64bit字）──→ 族A（6例致命）
        │    实测: 高16位+低位同时多位翻转
        │    机理候选: 同一字内多个弱单元（保持/读出噪声裕量不足）、
        │             阵列局部缺陷（局部工艺偏差）
        │
        └─ 形态3: 翻译路径瞬时错误 ────────────────→ 135次spurious（自愈）
             实测: L0 fault 合法地址 + 软件重走成功
             机理: TLB 项/page-walk cache 行 stale 或 corrupt

共性: 全部发生在"核私有、ECC/parity 未覆盖（或未检测）、高频访问"的路径上
传播: 错误数据 → 寄存器 → 指针运算 → 非规范地址/未映射地址 → 致命fault
     或 → 数据流 → 静默潜伏（SDC 的"静默"面：绝大多数错误读出并未崩溃，
       而是污染了计算结果后随进程继续运行；12次崩溃只是冰山露出水面的部分）
```

为什么 11/12 崩在调度器：192 核机器上 `find_busiest_group` 的 per-cpu
统计读是核内最热的 per-cpu 消费路径（每次 newidle balance 都执行，CPU179
作为被均衡对象被所有核读）。缺陷单元被高频访问，命中率最高。调度器只是
最频繁踩中缺陷的"矿工"，其自身逻辑没有问题。

SDC 定级：本故障是教科书级 SDC（Silent Data Corruption）：
无检测（RAS 零记录）、无纠正（无 ECC）、无隔离（错误数据随执行流传播）。
12 次崩溃是可见部分；按 135 次已观测警告与错误读出的比例推算，还有大量
未触发任何症状的污染数据（非指针数据被污染后不立即致命）已流入用户态计算。

## 4. 芯片设计与实现启示

### 4.1 微架构级：核私有 SRAM 的保护必须"全覆盖、真检测"

1. **L1D/L1I/TLB/walk-cache 必须有 end-to-end 保护，且保护位应随数据存入阵列**
   （inline parity/ECC，而非仅校验总线传输）。本案错误读出直接穿透到
   寄存器堆，说明至少存在一段"阵列→流水线"无校验路径。业界先例：
   IBM z 系列、Intel（L1D parity + 周期性 scrub）、AMD Zen（L1D parity）均
   对 L1 做 inline 保护。ARM 生态（服务器核）普遍只保护 L2/L3，本案证明
   这在 SDC 分级上是不够的。
2. **parity 至少要做到"检测后关闭核"**：L1 parity 命中时若无法纠正，应触发
   RAS 事件 + 核隔离，而不是静默。本案零检测 = 保护缺失或检测旁路。
3. **walk-cache/TLB 的管理结构建议加 parity**：页表走查缓存的位翻转直接
   产生"合法地址翻译失败"这类最难排查的故障形态（spurious fault）。

### 4.2 电路级：时序裕量与多位错误的物理根源

4. **stale 读（读回写前旧值）指向写路径/阵列更新的时序违例**：
   设计上应审查写穿透（write-through）到读出窗口的裕量，特别是
   同一 cache 行"高频写后长期只读"的访问模式（本案 __per_cpu_offset 正是
   该模式：boot 写一次，之后 22 天只读。只读热点是 stale 缺陷的天然探针，
   DFT 应覆盖此类 pattern）。
5. **同字内 2~7 位散布错误 = 弱单元聚集**：多位错误的纠错预算设计
   （SECDED 的 1-bit 纠正 + 2-bit 检测）在"聚集性弱单元"面前失效。
   建议：(a) 阵列 DFT 引入保留时间/读出裕量的角落扫描（corner screening）；
   (b) 若用 ECC，考虑 chipkill/符号级纠错以应对聚集性错误；(c) 交织
   （interleave）设计让一个物理字的不同位落在不同阵列区域。
6. **服务器 SoC 应提供"核级离线自检"LBIST/软件可见的健康度计数器**：
   让固件/OS 能在 RAS 报警之外发现"零报警但行为异常"的核。

### 4.3 架构级（RAS）：检测覆盖率要有"可观测性证明"

7. **RAS 架构必须可回答"哪些通路未受保护"**：本案 5 个 ERR 节点全部干净，
   给运维的假象是"CPU 健康"。设计上应把"未保护通路清单"作为交付文档，
   并在固件层提供错误注入验证（如 rasnode 的反向操作）证明检测真的会触发。
   ARM64 RAS（FEAT_RAS）只有实现者挂了检测才有记录。架构提供框架，
   不保证覆盖；服务器产品的 RAS 采购规格应逐单元要求覆盖率证据。
8. **错误拓扑上报**：一旦检测到核内错误，应上报精确到"哪个阵列/哪个通路"，
   便于像本案这样的定域（现在的 rasnode 只能读出"全零"）。

### 4.4 系统软件级：为"核也会撒谎"设防线

9. **内核 per-cpu 寻址可以低成本自防**：本案族 B 的直接死因是
   `__per_cpu_offset[cpu]==0`（未初始化哨兵值）未被防御。内核可加
   percpu 区访问的 debug 校验（CONFIG_DEBUG_PER_CPU_MAPS 全量校验；
   或至少对 offset==0 报 WARN 而非解引用），把"不可能的指针"挡在
   解引用之前，把 SDC 崩溃变成可诊断的 WARN。
10. **"spurious translation fault"应计入 RAS 计数器**：内核已在容忍这类
    故障（Ignoring spurious），但未累计上报。建议作为 per-cpu 软件计数器
    上报（类似 ARM64 的 CPU 误对齐统计），达到阈值触发核隔离建议。
    本案若早有此机制，135 次警告足以在第一次致命崩溃前把 CPU179 下线。
11. **调度域遍历的防御性校验**：find_busiest_group 这类"遍历指针链"的
    热路径可以低成本校验指针 canity（如顶 16 位==ffff），非致命分支兜底，
    避免 SDC 直接变成系统级崩溃。

### 4.5 验证与测试级

12. **把"只读热点 + 长时间运行"纳入 DFT/screening pattern**：
    本案缺陷在开机 418s~537ks 全程活跃，但只有高频只读访问才容易踩中。
    生产测试的 cache pattern 应包含"写一次→千万次读"的 aged-read 序列。
13. **故障注入应覆盖"核内 SRAM 读出错误"类 SDC**（本仓库 gem5-fi 的
    FI 方向）：现有 FI 多注入到寄存器/功能单元；本案证明"cache/TLB 阵列
    读出位翻转→数据流污染"是真实产品失效模式，FI 模型应补充
    L1D/TLB 阵列级注入，并评估软件防线（4.4 节）对这类注入的捕获率。

## 6. 结论

12 份转储拼出一个完整的微架构失效故事：一个物理核（CPU179）的私有
SRAM 读出路径存在固定缺陷，以三种形态（stale 读、多位翻转读、翻译瞬时
错误）持续 22 天输出坏数据；芯片的 ECC/RAS 体系对此完全沉默；错误的
数据污染指针后在调度器最热路径上引爆为致命故障；而更多的坏数据以
完全静默的方式流入了计算结果。这正是 SDC 的定义。

对芯片设计的最终启示可以浓缩成一句：在核内 SRAM 保护上省下的每一位
parity/ECC，都会以"零报警的谎报数据"形式连本带利地还给系统。
检测覆盖率不是架构规范里的一行字（FEAT_RAS 挂上了 ≠ 通路被保护了），
它必须逐单元验证、逐通路证明，并且要让软件在最坏情况下也能自保。

*报告日期：2026-09-05。证据基础：12 份 vmcore（共约 320GB）+ dmesg +
crash 8.0.4 + openEuler 6.6.0-145.3.23.154 vmlinux 调试符号。*

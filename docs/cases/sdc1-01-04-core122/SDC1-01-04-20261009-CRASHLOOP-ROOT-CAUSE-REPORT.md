## 0. 结论

**【实锤】一行结论**：10-09 全天 38 次自发复位 = **CPU122（MPIDR `0x0900060200`，9 月已定性的"水银核心"）的核内访存通路缺陷，在该核每次参与运行后数十秒内引爆内核 panic；panic 挂死后由 SBSA 通用看门狗（固件级，~900s 量级）热复位整机**，形成 17′12″ 周期循环。10-02 22:42 机架级冷上电（与 01-03 单板同时刻，互证为外部断电）后固件摘核态丢失、坏核回到启动集，是本次复发的起点。

**【实锤】指令级**（五次 panic 全部完成反汇编定位，**全部首错于 CPU122**，跨两个内核版本）：
1. **读已映射地址报 L3 翻译故障、pte=0**（上层 pgd/p4d/pud/pmd 全有效）——`gic_handle_irq+0x74` 读自身栈帧保存槽、`__switch_to+0xc8` 读 `next->thread.sctlr_user` 字段（两内核同偏移命中）；
2. **寄存器组被替换为其他合法内核数据**——x29/x19/x20/x21 被换成 idle 栈/vmalloc/ioremap 地址（x29 ≠ `mov x29,sp` 必保值，KASLR 无关的纯寄存器语义证明），SWAR 字符串常量四件套（`0101010101010101`/`7f7f7f7f7f7f7f7f`/`fefefefefefefeff`/`8080808080808080`）跨内核、跨会话复现；
3. **栈金丝雀读回失配**（`vsnprintf+0x6e8` `bl __stack_chk_fail`）。

**【强推】微架构级**：故障域收窄至该核**私有的访存行标识/请求-响应关联逻辑**——候选位点按单点解释力排序：**私有 L2 的 MSHR/响应关联结构 ＞ L1D tag 比较/way 选择（联合 PTW 读通路）＞ LSU store-buffer 转发 CAM**。排除共享层（同 cluster 的 CPU123/`0x0900060300` 健康）、排除 RF 位单元与执行单元（替代值为连贯的合法数据而非位翻转模式）。ECC/SECDED 全程无感——被替换与被"清零"的都是合法码字，这正是 9 月报告 D1/D2"有效数据错行替换"族的定义特征。

### 3.1 panic#5：gic_handle_irq（最近一次异常复位，全链路捕获）

**时间基准**：22:13:00 POST 开始（SEL）→ 22:14:55 引导交接（操作日志）→ 内核 t=0 ≈ 22:15:00（墙钟换算 ±15s）。

```
偏移    指令                                    运行时证据
+0x08   paciasp
+0x0c   stp  x29, x30, [sp, #-48]!             ★同页写 [0x…3d4000/08]
+0x10   mov  x29, sp                           x29 := 0xffff8000803d4000（dump=0xffff80008111bc00 → 被替换）
+0x14   stp  x19, x20, [sp, #16]               ★★同页写 [0x…3d4010/18]＝故障指令要读回的同一 16 字节
+0x18   adrp/add x19, gic_data+0x1e0           dump x19=ffff08208a4c3f00（vmalloc 区地址）→ 被替换
+0x20   stp  x21, x22, [sp, #32]               ★同页写 [0x…3d4020/28]
+0x24   adrp/add x21, percpu sgi_intid         dump x21=ffff80008111bdd0（idle 栈区地址）→ 被替换
+0x2c   ldr  x20, [x19, #8]                    x20 := GICC 基址
+0x30   add  x22, x20, #0xc                    x22 := GICC_IAR（MMIO）
+0x34   add  x20, x20, #0x10                   x20 := GICC_EOIR；dump x20≠x22+4 → 被替换
+0x38   b    +0x64
+0x40   str  w0, [x20]                         EOIR 写（MMIO）
+0x48~  tst/b.ne/dmb/mrs/str                   SGI INTID 记 percpu（另页）
+0x5c   ldr  x0, [x19, #1592]                  取 domain 句柄
+0x60   bl   generic_handle_domain_irq         x30:=+0x64（与 Oops lr 吻合）
+0x64   ldr  w0, [x22]                         IAR 读（MMIO）→ x0=0xa8c27bfd（成功）
+0x68   and  w1, w0, #0x3ff                    w1=0x3fd=1021（1020–1023 特殊区间，无中断可分发）
+0x6c   cmp  w1, #0x3fb
+0x70   b.ls +0x40                             不跳 → 中断已取尽，走尾声
+0x74   ldp  x19, x20, [sp, #16]               ★★★故障：读回 +0x14 写入的槽 → L3 翻译故障 pte=0
+0x78/+0x7c/+0x80/+0x84                       （未执行：ldp x21,x22 / ldp x29,x30 / autiasp / ret）
```

- **故障指令**：`a94153f3` 反汇编 `ldp x19, x20, [sp, #16]`；故障地址 `ffff8000803d4010`＝dump sp+0x10 严格一致——CPU122 的 per-CPU IRQ 栈内自身 48 字节栈帧中 x19/x20 保存槽（线性映射 phys 0x803d4000，帧恰落在 16KB 栈区边界）。
- **同页前驱**：`Code:` 窗口 4 条前驱（+0x64..+0x70）均不访问该页（IAR 读在 GICC ioremap 映射，and/cmp/b.ls 纯寄存器操作）；**已执行路径中访问该页的指令全部在序言且全部是写**（+0x0c/+0x14/+0x20 三个 stp）。写入与故障读回之间隔着完整一轮中断分发（`bl generic_handle_domain_irq` 整棵子树）。
- **寄存器替换**（KASLR 无关的语义判定）：

| 寄存器 | 指令流必有值 | dump 值 | 判定 |
|---|---|---|---|
| x29 | 0xffff8000803d4000（`mov x29,sp` 后全函数无 x29 写，被调方按 AAPCS 必须保存） | ffff80008111bc00（idle 任务栈） | **被替换** |
| x19 | gic_data+0x1e0（数据段） | ffff08208a4c3f00（vmalloc 区） | **被替换** |
| x20 | GICC_EOIR＝x22+4 | ffffdc58493700e8（ioremap 区、值不同） | **被替换** |
| x21 | percpu `sgi_intid` 基址 | ffff80008111bdd0（idle 栈区） | **被替换** |
| x30 / x22 / x0 / x1 | +0x64 / GICC_IAR / 0xa8c27bfd / 0x3fd | 同左 | 完好且自洽 |

- **推论**：Oops 调用栈中 `gic_handle_irq` 之后的帧（do_softirq_own_stack/irq_exit_rcu/…）是 unwinder 从**已被替换的 x29** 走进陈旧栈内容重建的，非本次真实调用链；真实语义链为 idle 循环 ← 中断进入 ← el1_interrupt ← gic_handle_irq。

### 3.2 panic#3/#4：__switch_to+0xc8（两内核同位点）

```
+0x00  paciasp / stp x29,x30,[sp,#-32]! / mov x29,sp / stp x19,x20,[sp,#16]
+0x10  mov x19, x1            ← x19 = next（task_struct*）
+0x14  mov x20, x0            ← x20 = prev
       …（FPSIMD/TLS/contextidr/current_task 切换）…
+0xc4  dsb  ish
+0xc8  ldr  x1, [x19, #5064]  ★故障：读 next->thread.sctlr_user（task_struct+0x13c8）
+0xcc  ldr  x0, [x20, #5064]  （读 prev->thread.sctlr_user）
+0xd0  cmp  x0, x1 / b.eq … / mrs x2, sctlr_el1 …
```

panic#4 中 x19=`ffff80008db23c70`，+0x13c8 = **`ffff80008db25038`＝故障地址精确命中**——对**正在运行的 kworker 的 task_struct 字段**（必然已映射）的加载，页表走行得 pte=0（pgd/p4d/pud/pmd 有效）。panic#3 的 `Code:` 窗口 `d503201f d503201f d503201f d5033b9f (f949e661)` 与静态反汇编一致（其中一条 b→nop 为运行时 alternatives 补丁，不影响分析）。两版内核该函数符号地址相同（154→167 增量未改动此函数），同偏移命中非巧合。

### 3.3 panic#1：vsnprintf 金丝雀（.3.154）

`vsnprintf+0x6e8 = bl __stack_chk_fail`（0xffff800080ee9de0），+0x6ec 为其返回地址（panic 消息所引）。序言存入栈帧的金丝雀与尾声读回值失配——读侧或写侧至少一侧被错行替换。无 Oops 寄存器转储（panic 直调，非异常）。

### 3.4 panic#2：PC=0x0（.4.13.167）

`pc:0x0 lr:0x0`、`Code: ????????`（取指流完全不可读）——x30/PC 类寄存器被垃圾数据污染后跳转的下游表现；寄存器组同时含 SWAR 常量与字符串碎片（x24="data_loc"、x19="apter_nr" 等），与 9 月 Boot 1/3 的"寄存器组剖析"形态一致。

## 4. 传播链与 17′12″ 周期算术【实锤】

```
CPU122 缺陷激发（启动风暴/核上线/中断处理，见 §5.4）
  → 内核 panic（10-09 各 boot 于 t≈30–37s；boot D 于上线后 27s）
  → panic 路径挂死（panic=30 的重启未触发：任务栈转储阶段死锁；早期 boot 时 kdump 未就绪）
  → SBSA 通用看门狗超时（固件日志：NOTICE: SBSA watchdog timeout, hot reset system）
  → 整机热复位 → SEL "System Restart" → 下一次启动 → 循环
```

- **周期分解**：POST ~115s（22:13:00→22:14:55 实测）+ 内核至 panic ~30s + 看门狗 ~885s ≈ **1032s = 17′12″**，与 10-03/10-09 午后观测周期吻合。
- **boot D（定向复现）链**：CPU122 上线（23:34:44，t=4784.3s）→ +17ms 调度域 WARN（`kernel/sched/topology.c:1021`，cpuhp/122）→ +27.08s 致命 Oops（23:35:11）→ kexec kdump（23:35:12，此刻 Kdump: loaded）→ **12′07″ 后 SBSA 看门狗热复位（23:47:19）**。
- **kdump 失败机理**：崩溃内核 12 分钟内未完成 vmcore 落盘即被看门狗中止；**/var/crash 为空（10-10 已核实）**——pte=0 的"PTE 内存真值"判据丢失（§6）。

## 5. 微架构级根因定位

### 5.1 现象 → 流水线结构映射【实锤（现象）→ 强推（映射）】

| # | 观测（实锤） | 指向的结构 |
|---|---|---|
| A | 寄存器组被替换为**其他合法内核数据**（idle 栈/vmalloc/ioremap 指针；SWAR .rodata 常量；printk 字符串碎片） | 装载返回通路（L1D 命中数据选择 / 未命中路径响应关联 / LSU 转发）把**别的行**的数据送入 RF 写端口 |
| B | 读**必然已映射**的地址（自身栈帧槽、运行中 task 的 sctlr_user 字段）报 L3 翻译故障、**pte=0** 且上层表项有效 | 页表走行（PTW，绕过 L1D，经私有 L2）读出 0——或 PTE 真被清零（写侧，见 D） |
| C | 栈金丝雀写后读失配（vsnprintf） | 同 A/B：栈访问的写-读不对称 |
| D | （9 月）页表页被零化/被代码字节覆写，**跨核可见** | store 提交/写回落错行——真实内存被写错 |
| E | 取指流垃圾（PC=0x0，Code 不可读） | x30/PC 被污染的下游，非取指通路原发 |

### 5.2 故障域收窄【强推】

1. **排除共享层（L3/HHA、DDR、互连、GIC）**：同 cluster 的 CPU123（`0x0900060300`，与坏核共享 L3 slice/簇互连）两度证明健康——9 月 Boot D 以其顶替逻辑 CPU122 干净启动；10-10 当前 `0-121,123-127` 在线稳定。其余 126/127 核长期正常。
2. **排除 RF 位单元与执行单元**（弱排除）：四个被替换寄存器的值是**连贯的合法内核地址**而非粘滞位/随机翻转模式；若是 RF 位单元缺陷，腐化模式应与载荷无关且呈位级特征。旁路网络误关联仍属候选（见 5.3③）。
3. **排除平台级诱因**（电源/热）：BMC 传感器全天正常（复位前后 Core 52°C、入口 31°C、12V 轨 11.82V、PSU 413W、PwrOk 无跌落、Watchdog2 无断言）；10-03 入口温事件与复位无时间因果。满载非必要条件（见 5.4）。
4. **收敛**：缺陷位于 `0x0900060200` **核私有域**——L1D（tag/way/数据选择）、私有 L2（tag/MSHR/写回）、MMU/PTW 读通路、LSU（store buffer 转发 CAM）、以及核内结果旁路网络。

### 5.3 缺陷机制假说（按单点解释力排序）【假设，附判别】

| 序 | 候选位点 | 解释力 | 未覆盖项 |
|---|---|---|---|
| ① | **私有 L2 的请求-响应关联（MSHR/in-flight 跟踪、响应写回选择）** | 单点统一解释 A（未命中装载返回他请求数据）、B（PTW 经 L2 读 PTE 得 0）、D（store/写回落错行） | 要求全部出错装载均为 L1D 未命中（栈帧槽经深调用树驱逐后未命中，成立但不能从控制台证明） |
| ② | L1D tag 比较/way 选择 + PTW 读通路（双位点） | 解释 A（命中错 way＝同组他行数据）+ B | 需两个独立缺陷， parsimony 差；但 .rodata 常量经未命中进入后驻留 L1D、再被他行"错 way"读出亦自洽 |
| ③ | 核内旁路/转发网络误关联 | 解释部分 A（他指令结果直入 RF） | 不解释 SWAR .rodata 常量到达寄存器（除非经装载）；不解释 B/D |
| ④ | LSU store→load 转发 CAM 误命中 | 解释 C 及部分 A | 不解释 .rodata 常量（转发只能给出 store buffer 内数据）、不解释 B |

**共同约束**（所有假说须满足）：(a) 被替换值皆为合法码字 → 任何带 ECC/奇偶校验的阵列不报警 → 缺陷在**选择/关联逻辑**而非数据阵列位单元；(b) 触发需访存活动密度（5.4）；(c) 跨内核版本、跨启动模式确定性定位于同一物理核。

### 5.4 触发条件画像【实锤】

- 全部已知出错时刻均处于**高装载未命中密度窗口**：9 月为模块装载 memcpy + printk 风暴（19–34s）；10-09 晨间为 udev/核上线风暴（t≈35s，上线后 9–19ms 出事）；boot D 为中断深调用树（嵌套中断、IRQ 栈逼近 16KB 底缘）。
- **不需要用户负载**：boot D 中 CPU122 上线后 27 秒处于纯 idle（无任何任务调度到该核），一轮中断处理即自发致命——缺陷在正常内核活动量下即可激发。
- 与温度/功耗/平均负载无阈值关系（传感器全天正常）。

### 5.5 与 9 月报告的承接

9 月报告定性为"核内（或私有 L1D/L2）装入返回通路/存储提交通路的行标识故障，D1/D2 错源/错行替换族"。本案新增证据**确认并细化**：(1) 寄存器级替换直接观测（9 月仅经 panic 转储间接推断）；(2) PTW 读通路异常（pte=0）为新观测面；(3) 跨内核版本同指令位点复现；(4) 触发画像从"启动风暴"扩展到"任意访存密度窗口含 idle 中断处理"；(5) 传播链补全（SBSA 看门狗→17′12″ 循环）。

## 7. 处置状态与建议

**当前状态（10-10 13:30）**：机器以 127 核（CPU122 offline，0-121,123-127）稳定运行；历史验证——nr_cpus=12 boot 干净、maxcpus=122+禁自动补上线稳定 11h+、当前逐核 offline 方案稳定。

1. **持久化隔离**（按优先级）：① 开机自动 offline cpu122（udev 规则或 systemd oneshot，echo 0 > online——当前方案固化）；② BIOS 级核禁用（若 J353 BIOS 提供 Active Processor Cores/逐核控制）；③ `nr_cpus=122`（硬上限 possible 集，热插拔无法越过；注意会同时屏蔽 CPU123）。
2. **该 die 送厂 FA**（9 月建议维持并强化）：本案提供了 FA 迄今最完整的单核证据包——五次 panic 指令级现场、寄存器替换对照表、同页写读不对称现场、跨内核复现。重点检查（按 5.3 序）：私有 L2 MSHR/响应关联 → L1D tag/way 选择 → PTW 读通路 → LSU 转发 CAM。
3. **kdump 可用性**：与 SBSA 看门狗冲突必须解决，否则该机永远拿不到 vmcore。
4. **控制台**：cmdline 建议加回 `console=ttyS0,115200`（当前 tty0 使 SOL 失明，黑匣子仍可用但串口接管无效）。

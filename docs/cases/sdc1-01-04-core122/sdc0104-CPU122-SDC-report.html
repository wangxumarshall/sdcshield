CPU122 热插上线触发 Kernel Panic
根因分析报告（定位至 CPU 微架构级）

对启动串口日志中由 122 核导致的 kernel panic 进行逐寄存器、调用栈、内存值取证，结合 Linux 6.6 arm64 内核源码与官方内核镜像反汇编，将故障定位到物理核 CPU122 的架构状态 / MMU 页表遍历子系统的间歇性硅缺陷。

CPU122 是一颗间歇性失效（marginal / bad silicon）的物理核。 它在热插上线与 cpufreq（DVFS）初始化的特定窗口内，偶发地破坏自身架构寄存器状态 / MMU 三级页表遍历，对一个实际可读的 vmalloc 页抛出伪三级翻译故障（spurious level-3 translation fault）。4 次启动中前 2 次必崩、后 2 次正常，且崩溃只发生在 CPU122；同核在健康启动时寄存器为正常线性指针，崩溃时出现健康执行不可能的寄存器值。确定性代码缺陷不可能如此挑核、又间歇自愈，故根因锁定为该物理核，建议将其永久下线并向厂商 RMA。

04ESR 与数据异常逐位解码

ESR_EL2（内核运行于 EL2）= 0x96000007。EC 指明异常类别，IL 为指令长度，ISS 为综合信息。

位段值含义
EC[31:26]0x25DABT（current EL）：数据访问异常，且未改变异常级别（不是来自更低 EL）
IL[25]1故障指令为 32 位定长（AArch64）
ISV[24]0指令综合信息无效：CPU 未能在 ISS 中给出故障指令的目标寄存器/传输细节，故只能靠 pc + 反汇编定位（ISV=0 常见于页表遍历本身失败）
SAS/SSE/SRT/SF—因 ISV=0，访问大小、符号扩展、目标寄存器号等字段均无意义
EA[11]0非外部异常（不是来自总线/控制器的外部中止）
SET[9:8]0同步错误类型为 0（非 Unrecoverable/Unexpected/Uncategorized）
FnV[7]0FAR 有效：FAR_EL2 中的故障地址 ffff80008bdfcf58 可信
WnR[6]0读访问（write-not-read=0）；故障由一条 load 触发，不是 store
FSC[5:0]0x07三级翻译故障（level-3 translation fault）：页表遍历走到第 3 级（PTE），描述符无效
ISS20x0CM=0、TnD=0、TagAccess=0、GCS=0、Overlay=0、DirtyBit=0、Xs=0——无内存标签、GCS、覆盖/脏位等附加因素
关键点：这是一个发生在读、当前 EL、第 3 级 PTE 的翻译故障，且 ISV=0（页表遍历自身失败，CPU 无法补全指令信息）。它既不是外部/总线中止（EA=0），也不是标签检查、权限故障（权限故障的 FSC 会是 0x0C/0x0D/0x0F），而是“第 3 级描述符无效”。

反汇编结论：故障指令读取的正是 next->thread.sctlr_user。健康执行中 next 是合法 task_struct、该字段必然可读；崩溃核在同函数内 x19/x20 已异常，且对一个此前微秒还能读的页报 L3 缺页。

07完整触发链与源码对应

崩溃发生在 CPU122 热插上线（cpuhp）过程中 cpufreq/DVFS 初始化窗口。热插线程 cpuhp/122(PID3098) 需要读取 CPU122 的 AMU 性能计数，通过 smp_call_on_cpu 把回调投到 CPU122 本地；执行该回调的工作线程是 kworker/122:3(PID3106)。崩溃点在 CPU122 调度切换（__switch_to）该工作的瞬间。

08根因：定位到 CPU 微架构

综合寄存器、ESR、页表与反汇编，证据链指向：CPU122 这一颗物理核存在间歇性（PVT 相关的 marginal/bad silicon）失效，在热插 + DVFS 初始化窗口内偶发破坏自身架构寄存器状态 / MMU 三级页表遍历，对一个实际可读的页抛出伪 L3 翻译故障。

8.1 决定性矛盾：同一 4K 页“先成功读、后报缺页”

在崩溃核同一次 __switch_to 调用中，x19 指向的同一个 4K 页 ffff80008bdfc000 被访问三次：

指令位置访问地址（页内偏移）结果说明
+0x058…fc000 + 0xb98成功LDR x0,[x19,#0x1008]（读 next 的 TPIDR/线程指针）
+0x068…fc000 + 0x3b0成功LDRSW x0,[x19,#0x820]（读 next 的 context_id）
+0x0c8…fc000 + 0xf58L3 缺页LDR x1,[x19,#0x13c8]，oops 却报该页 PTE=0
逻辑矛盾：同一 4K 页的 PTE 只有一个。它在 +0x058/+0x068（仅早几十~几百纳秒）还判定有效并成功取数，到 +0x0c8 不可能“同一 PTE 变成 0”，除非——(a) 该页在两次访问之间被解除映射，或 (b) CPU122 的 MMU 遍历 / load 通路把有效 PTE 误判为 0。

8.2 排除“运行中解除映射”，锁定核级误判

该页是存活 task_struct故障对象是正在被调度切换的 next 任务；内核不存在“在几十纳秒内 unmap 一个存活 task_struct 所在页”的路径（已核 mm/vmalloc.c、mm/secretmem.c、kernel/power/snapshot.c：仅 memfd_secret 与休眠会持久失效线性映射，均不适用）。
无调试型拆页机制CONFIG_DEBUG_PAGEALLOC / PAGE_TABLE_CHECK / KFENCE 均未设置（官方 IKCONFIG 核实），不存在主动把页表项周期性清零的机制。
task_struct 本不该在 vmallocx19 落在 vmalloc 区，而 slab 对象（task_struct）必须位于 ffff0/ffff7 线性区——这本身证明 x19 的值已被破坏，故障页地址是“坏指针 + 偏移”算出来的。

8.3 架构寄存器状态被破坏（x19 / x20）

寄存器崩溃值违反的约定
x19ffff80008bdfbb90（vmalloc）序言 +0x10 唯一一次写 x19=next，必须是线性区合法 task_struct
x200x7a = 122（小整数）序言 +0x14 唯一一次写 x20=prev，必须是指针；核号 122 出现在本应是 prev 指针的寄存器中

对照：健康启动（Boot3）同流程现场寄存器全部健康（x19=ffff082101fac688、x20=ffff0820e24afa08，均线性指针）；崩溃核的调度器其它结构指针（x22/x24/x25）也仍是健康线性指针。破坏是局部、选择性、仅发生在 CPU122 的——这是硅级间歇失效的典型形态，而非软件系统性错误（软件错误会在任意核、以确定方式复现）。

8.4 触发窗口：热插 + DVFS，PVT 相关的间歇性

启动CPU122 上线 / 结果现象
Boot136.159 上线 → 36.169 崩上线后约 10ms，DVFS 初始化读 AMU 时崩溃
Boot2上线后即刻崩（行18143）现场与 Boot1 逐字节相同
Boot336.328 上线，未崩仅 plist QoS WARNING（独立软件小问题）

同一颗核、同一软件流程，两次崩、两次不崩——非确定、与上线/调频窗口强相关。cpufreq_online 阶段伴随频率/电压（DVFS）切换，是核内时序裕量最紧张的时刻；marginal 硅片在特定 PVT（工艺-电压-温度）工作点最易暴露，电压过渡完成、时序放宽后又可“自愈”，完美解释间歇性。

8.5 微架构功能块定位

MIDR = 0x480fd020implementer 0x48 HiSilicon · part 0xd02 = HISI_CPU_PART_LINXICORE9100（hip09 / 灵犀） · variant 0xf · revision 0（r0p0）；全机 128 核 MIDR 相同
微架构6 发射（2 分支 + 6 ALU + 4 FP + 2 load + 2 store）、64KB L1、512KB L2；SVE/i8mm/bf16/rng/bti/ecv/ssbs 等
症状 → 功能块 ① load 对有效页报 PTW 第 3 级描述符无效（有效 PTE 被误读为 0）→ MMU 页表遍历器（PTW）/ TLB 缺失填充路径，或 load 队列→L1/数据读取通路；
② GPR x19/x20 被改成不相干值（vmalloc 地址、核号 122）→ 整数物理寄存器文件 / 写回或操作数转发（bypass/forwarding）网络、或推测/异常检查点恢复路径。
统一解释两类症状最自洽的共同成因是核内 PVT 相关时序裕量不足（setup/hold 违例）或弱驱动/间歇开路：在 DVFS 过渡工作点偶发使 PTW 对描述符采样错误、寄存器写回/保持出错；工作点离开后恢复正常。
定位粒度与边界无 ATPG/扫描链与芯片内部波形，无法再下钻到具体门/触发器；但已定位到核内 “load/MMU-PTW + 寄存器文件/转发”微架构功能域，判定为 PVT 相关间歇性硅缺陷，且可通过隔离/更换该核 100% 规避。

8.6 已知勘误背景（佐证与排除）

勘误 / 开关状态与本案关系
HISILICON_ERRATUM_162100125=yLINXICORE9100 r0p0、需 supports_cnp，效果为禁用 CNP TLB 优化。证明该 stepping 确有 TLB 类已公开勘误；但本次在 CNP 已禁用下仍发生，且伴 GPR 损坏，现象超出该勘误 → 倾向该颗个体硅缺陷而非可软件 workaround 的批量勘误。
arm64.nopauth（命令行）已禁用指针认证关闭，排除 PAC/签名相关故障。
HIP08_RU_PREFETCH=y 但不匹配match 仅 TSV110(0xd01)，本核为 0xd02，不生效。
HISILICON_ERRATUM_1980005未设IDC 相关，与本案无关。
根因结论（高置信度）：CPU122（LINXICORE9100 r0p0 中一颗特定物理核）为间歇性失效的 marginal/bad silicon，在热插 + DVFS 工作点偶发破坏自身寄存器状态与 MMU 三级遍历，抛出伪 L3 翻译故障。非软件 bug、非内存条故障（0 hwpoisoned、约 59GB 空闲、EA=0）。

09排除项与取证局限

9.1 系统性排除

候选原因判定依据
软件 bug（内核/调度/CPPC）排除软件错误应在任意核、以确定方式复现；本案仅 CPU122、间歇（2 崩 2 不崩），且故障点 20 字节与官方镜像逐字节一致。Boot3 的 plist WARNING 是独立软件小问题，现场寄存器健康，与 panic 无关。
内存条 / 物理内存损坏排除EA=0（非外部/总线中止）、hwpoisoned=0、约 59GB 空闲无压力；其它 127 核与同页其它偏移访问正常；坏内存会在地址/核上随机分布，不会锁定同一核号。
外部 / 总线 / SMMU 异常排除EA=0、SET=0；故障是 CPU 核内 load，不经过 SMMU。
权限故障（AP/UXN/PXN）排除FSC=0x07 是翻译故障（描述符无效），权限故障应为 0x0C/0x0D/0x0F 等。
MTE 内存标签 / GCS / 覆盖脏位排除ISS2 全 0（TagAccess/GCS/Overlay/DirtyBit=0）；CONFIG_ARM64_MTE 未设置。
指针认证（PAC）排除命令行 arm64.nopauth 已禁用。
已公开勘误（CNP 等）基本排除162100125 的 CNP workaround 已生效仍崩，且伴 GPR 损坏，现象超出公开勘误。

9.2 取证局限（须如实标注）

APTE 真相不可由串口单独判定：oops 的二次页表遍历也运行在嫌疑核 CPU122 上，故“pte=0”无法区分“内存中真为 0”与“核把有效 PTE 误读为 0”。但 8.1 的“同页先成功读、后报缺页”在软件层面无解，强烈指向后者。
Bx20=122 的两种并存解释：(i) CI 临时构建的寄存器分配与官方发行镜像不同；(ii) 核级状态破坏。故障点前后 20 字节与官方 Image 逐字节一致（说明运行的就是该镜像），且 x19 同时异常，使 (ii) 更可信，但无法仅凭静态反汇编 100% 排除 (i)。
C无完整 vmcore：虽配置 crashkernel=1024M,high，但本串口日志（恰好 2MB）未记录 kdump 完成；日志为环形/截断输出，未含崩溃后用户态转储。拿到 vmcore 可用 crash 直接读取 PTE 物理内存与全部任务，一锤定音区分局限 A。
D微架构下钻边界：无芯片内部波形、扫描链/ATPG 与厂商 RAS 详细日志，无法定位到具体门/触发器，只能到“load/MMU-PTW + 寄存器文件/转发”功能域并判定 PVT 相关间歇失效。

10处置与验证建议

10.1 立即止血：把 CPU122 永久排除出调度

# 运行时下线（立即生效） echo 0 > /sys/devices/system/cpu/cpu122/online # 阻止其被自动热插：udev 规则（固化） # /etc/udev/rules.d/90-cpu122-offline.rules SUBSYSTEM=="cpu", KERNEL=="cpu122", ATTR{online}="0"

命令行已有 maxcpus=122（启动只带 0–121），但日志显示 CPU122/123 在启动后约 35–36s 被热插拉起（CPU123 35.293、CPU122 36.159）；故必须同时禁止对该核的自动 online，仅靠 maxcpus 不够。也可用 nr_cpus / maxcpus 配合关闭对应核的热插服务。

10.2 缓解：绕过 DVFS 触发窗口

固定该核频点若业务必须使用该核，将其 cpufreq 锁定在已验证稳定的频点（cpupower frequency-set -c 122 -f <稳定频点>），避免在该核上做频率/电压切换；上线后再固定，避开崩溃窗口。
减少热插频次避免对该核反复 online/offline；如使用 tuned/容器 cpuset，勿把任务调度到 122。

10.3 根治：报修更换

该核是 HiSilicon 服务器 SoC（LINXICORE9100）封装内的一个物理核，硅缺陷无法在现场修复，应凭本取证向整机/主板（BC83AMDA01-7270Z）供应商报修，更换对应 CPU/主板；并要求厂商用其 RAS/诊断套件对该 SoC 做核级测试与内部错误记录（RAS/MCE、AMU、内部计数器）核对。

10.4 复现与验证

提高复现率对 CPU122 定向：反复 online/offline + 频率/温度循环（cpupower 频点扫描）+ stress-ng --taskset 122 --cpu N（含 SVE/i8mm 负载），在升温与 DVFS 切换下最易触发。
补齐 vmcore确认 kdump 正常（crashkernel 已预留），下次崩溃用 crash 读取 PTE 物理内存与全部 task_struct，直接区分局限 A/B；同时开启 EDAC/RAS、收集该核 SError/CMCI。
更换后验证更换后对新核长时间跑上述定向压测 + 全机热插循环，确认无复现；保留本报告的寄存器/页表基线作为对照。

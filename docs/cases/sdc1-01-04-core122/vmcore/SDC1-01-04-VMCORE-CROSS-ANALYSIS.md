# sdc1-01-04 三份 vmcore 跨案综合分析：CPU122"水银核心"的隔离期表现图谱

> **报告日期**: 2026-10-10
> **取证对象**: `/home/sdc/vmcore/` 下三次 kdump 捕获（9-29 / 9-30 / 10-09），分报告见同目录三篇
> **先验证据链**: 《SDC1-01-04-CPU122-MICROARCH-DIAGNOSIS-REPORT.md》（9-17/9-18 微架构诊断：物理核 MPIDR `0x0900060200` = 逻辑 CPU122 存在核内数据通路"有效数据错行替换"缺陷）与《SDC1-01-04-CPU122-BOOT-ISOLATION-CONFIG.md》（maxcpus=122 启动隔离 + 六层捕获体系）
> **本文定位**: 三案的横向综合——**在坏核受控上线（封顶 1.45/2.0 GHz + 全核压力）的实验窗口内，CPU122 以至少六种可区分的形态反复发生核内数据通路故障，其中 bit 15（0x8000）单比特形态跨案三连发，且首次获得用户态位级直接检出（xor=0x00008000）**。本文给出表现图谱、微架构归因、频率-存活对照与运维建议。

---

## 0. 一页结论

三份 vmcore 是坏核隔离体系建成后的首批完整捕获（9-22/9-23 部署，正本 `~/vmcore-project/`）。三案共同点：

1. **案发 CPU 全部锚定 CPU122（0x0900060200）**：三案 panic 任务均在 CPU122；10-09 的五事件弧中四个在 CPU122/线程 122，第五个（E2）是对污染状态的跨 CPU 消费；所有"邻居对照"（rq121/123、cpu_irqtime[121/123]、CPU119/120/121/123 的 kmalloc-4k freelist）全部健康。
2. **单比特位错的位位置集中**：bit 15（0x8000）三连发（9-29 x21 寄存器、10-09 E1 pcp 链指针、10-09 用户态数据字）；另有 bit 61（10-09 故障地址顶字节）、bit 2（9-30 SPSR 模式域）——**缺陷对 bit 15 有显著偏好**，指向数据通路中某个特定位单元/通道。
3. **"有效数据替换"形态贯穿**：8 个 ASCII 空格充当 freelist 指针（10-09）、陈旧栈指针充当 SP（9-30，指向已释放 vmalloc 空洞）、不可推导外来值充当 x19（9-29）、比真实时刻旧 3.1044 s 的时钟值（9-29）——被交付的都是"别的地址/别的时刻的合法内容"，ECC 全程无感，与 9-17 报告 D1/D2 族完全一致。
4. **用户态探测对内核态损坏不可见**：9-29（62/62 pass）、9-30（35/35 pass）两案探测零检出即崩溃；10-09 案探测两次检出（08:09、11:15）而致命损坏仍在内核态——**"探测 pass"不能作为坏核健康的证据**。
5. **频率-存活梯度再获数据点**：2.9 GHz 即崩（9-22 史实）→ **2.0 GHz 活跃出错（10-09：3 小时内 5 事件，含用户态 bit15 检出）** → 1.45 GHz 出错但可存活 19 分钟~5 天（9-30 / 9-29）。
6. **六层捕获体系按设计工作**：三次 panic 全部成功 kdump（37 秒级完成）、panic_on_warn=0 使 DEBUG_LIST 两次拦截后系统存活至致命点、netconsole/SEL 静默侧证（RAS 无感）。

**综合置信度：高**（P1 单核浓度跨三案成立、P2 复发、P3 RAS 静默、P5 位级签名）。处置维持既有结论：启动隔离 + 实验窗口受控上线 + 送厂 FA。

## 2. 缺陷表现图谱（六形态）

| # | 形态 | 案例 | 证据要点 | 通路侧 |
|---|---|---|---|---|
| F1 | **寄存器组替换（外来值）** | 9-29 x19 | 数学必为 0 的槽位出现 6.9×10¹⁵ ns 不可推导值 | 读/操作数侧 |
| F2 | **寄存器单比特清除** | 9-29 x21（bit15）；9-30 SPSR（bit2，佐证） | 与同函数内已验证值差恰一比特 | 读/操作数侧 |
| F3 | **SP 替换（陈旧栈状值）** | 9-30；9-17 Boot 1 同形态 | 值指向已释放 vmalloc 空洞；几何 (栈基−0x8000)+小偏移跨会话复现 | 读/操作数侧 |
| F4 | **时钟读数陈旧交付** | 9-29 前置 | 单中断窗口内 ≥2 次连续读数低 3.1044 s 后恢复（"停顿"假说被三重矛盾排除） | 读侧（LSU/计数器读） |
| F5 | **per-cpu/slab 状态污染（陈旧文本为指针）** | 10-09 E3 | freeptr 槽=8 空格（旧文本）；三个对象同态；邻居全健康 | 读侧取出旧行 或 写侧存储未落点 |
| F6 | **链表/数据字单比特位错** | 10-09 E1（bit15）；10-09 用户态字（bit15）；10-09 地址通路（bit61） | 差值恰 0x8000/顶字节；用户态直接捕获 xor=0x00008000 | 读/写/地址生成侧 |

**图谱解读**：六形态全部落在**核内私有域**（寄存器堆、操作数/地址生成、LSU 装载返回、存储提交、per-cpu 数据的核内视图），无任何共享层（LLC/HHA、DDR、互连、GIC）牵连证据——与 9-17 报告 Boot D 单变量 A/B（摘除 0x0900060200 后干净启动）的定位一致。

### 2.1 bit 15 集中的意义

三案中 bit 15（0x8000）以三种不同载体独立出现：

| 载体 | 期望值 | 实测值 | 差 |
|---|---|---|---|
| 9-29 x21（rq 指针寄存器） | 0xffff082f7f1b**f**6c0 | 0xffff082f7f1b**7**6c0 | 0x8000（清除） |
| 10-09 E1 pcp 链 next->prev | 0xffff082ffffc**5**980 | 0xffff082ffffc**d**980 | 0x8000（置位） |
| 10-09 TEST#13 用户态字（index 970） | 0x9738**C**0D8 | 0x9738**4**0D8 | 0x8000（清除） |

若位错在 64 位数据通路均匀分布，三连中同一位（还包括 bit61/bit2 的旁证）的概率极低。**位位置集中指向：数据通路中某个特定位单元（如某流水线寄存器/填缓冲/存储缓冲项的 bit15 单元）存在物理缺陷**——为送厂 FA 提供了明确的失效单元假设。bit 15 = 32 位子字内 byte1 的最高位，恰为 SWAR/SVE 128 位通道的中间边界位，与实验负载（SVE 字节交换/SWAR 字符串操作）的高频翻转窗口重合。

### 2.2 "有效数据替换"与 ECC 静默的再证实

三案所有被交付的"错误值"都是**别处/别时刻的合法内容**：8 空格（文本行的真实内容）、陈旧 SP（某已消亡栈的真实指针）、外来 ns 值（真实时间量级的数据）、旧时钟值（真实旧计数）——SECDED 对合法码字全无感知，RAS 全程静默（三 boot 的 SEL/内核 EDAC 零事件）。这是 §10.7.6"RAS 静默 + 持续崩溃 = 通路故障强信号"判据的第三次跨会话验证。

## 5. 微架构归因（综合）

**定位**：0x0900060200 核内私有数据通路（装入返回通路 / 存储提交通路的行标识/位完整性），9-17 报告 D1/D2"有效数据错行替换"族。三案新增的画像细化：

1. **行标识故障的"陈旧行"亚型**：9-30 的 SP（旧栈指针）、9-29 的时钟（旧计数值）、10-09 的 freeptr（旧文本）——三案均为"**交付了该地址/该通路早先的合法内容**"，而非随机位翻转；
2. **位缺陷亚型**：bit15 三连发 + bit61/bit2 旁证——通路中存在**特定位单元的物理缺陷**，在陈旧行交付之外独立表现；
3. **形态与负载相关性**：三案根因事件全部位于**调度器 tick / 中断返回 / 分配器热路径**（rq 链、irqtime/sched_clock、pcp/slab freelist）——这些路径的访存密度与缺陷触发高度相关；两案的用户态检出（neon_rot 的 SVE 装载序列、probe_x 的字节交换往返）表明**用户态数据通路同样暴露**；
4. **健康核负证据**：所有邻居对照（跨簇 rq121/123、cpu_irqtime、CPU119/120/121/123 的 slab freelist、CPU19 的同代码告警形态）全部正常/为代码伪影——污染不留共享层痕迹。

**置信度（§10.9.3 七步法）**：P1（单核浓度，三案+用户态检出全在 122）√；P2（复发，跨 9-17/9-29/9-30/10-09 四个会话）√；P3（RAS 静默）√；P5（加权：SP-relative、嵌套故障、位错签名）√ → **高置信：水银核心，维持隔离与 FA 建议**。

## 6. 处置与后续建议

1. **隔离与协议**（维持）：`maxcpus=122` 启动隔离、实验窗口 `cpu122-online-offline.sh` 正门 + 封顶 + MPIDR 核对；**udev 规则注释的周期性核查**（9-24/9-29 两次击穿的根因，升级 dnf 后必查，见背景文档 §6.2）。
2. **"探测 pass ≠ 健康证"**：案①②探测零检出即崩——实验判定应同时看：探测结果、dmesg 的 DEBUG_LIST/WARN 事件、机器存活；建议狩猎框架把 `journalctl -k` 的 list corruption/Oops 关键字纳入每项测试的判定项。
3. **工具链注意**（本三案实测）：① crash 8.0.4 对 openEuler 定制入口的 bad-stack 帧有 16 字节解析偏移——以 `rd` 原始内存 + dmesg 对照为准；② `search -k` 在 makedumpfile PARTIAL DUMP 上静默失效，不可用于"值不存在"论证；③ 后续捕获若需追"替换值的来源"，建议临时改用 `-d 11`（保留用户页与缓存页）级别转储。
4. **送厂 FA 的失效单元假设**：bit15 位单元 + 陈旧行交付；附三案证据链与本图谱。
5. **频率研究**：2.0 GHz 档已证活跃出错；1.45 GHz 档并非安全（案①②）——若继续频率扫描，建议把"用户态 bit 级检出率"（xor 分布直方图）作为比"存活/崩溃"更灵敏的观测量。

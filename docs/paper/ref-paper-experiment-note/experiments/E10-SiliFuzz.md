## 1. 研究问题与核心贡献(≤5 行)

研究问题:在没有 RTL、CPU 对用户不透明的约束下,如何大规模发现已部署商用 x86_64 CPU 的电气缺陷(electrical defects,单芯片/单核级,非全微架构级 logic bug)。
方法:"fuzzing by proxy" —— 用覆盖引导的软件 fuzzing 去 fuzz CPU 的软件代理(模拟器、反汇编器),把语料(corpus)在真实 CPU 大规模执行、跨核交叉验证。
核心产出:约 500,000 snapshot 的语料部署到 Google 生产集群大部分机器,检出多台缺陷机;约 45% 的发现是任何其他工具/自动化未曾识别的;4 组深入分析的缺陷(附录 A–D)+ 通用缺陷模式清单。

## 2. 实验方法(生成器架构、覆盖指标定义、评估闭环)

### 2.1 总体架构(§2,四组件)

- **Snapshot(§2.2)**:表示并序列化"短小、自包含程序 + 参考输出"的格式;
- **Player(§2.3)**:逐个执行 snapshot 的程序(CPU 或模拟器上);
- **Snapshot 生成(§2.4)**:生成 snapshot 集的流水线,目标覆盖尽可能多的角落案例;
- **大规模执行(§2.5)**+**反馈环(§2.6)**:集群筛查 + 已知坏机反哺语料。
- 全部在用户态运行,不直接测试内核态指令。
- "覆盖"定义(§2.1):软件控制流**边覆盖**(edge coverage)。

### 2.2 Snapshot 格式(§2.2)——语料构造核心

- 典型 snapshot:**少于 100 字节代码**,微秒级运行;但格式可任意大。
- 合法 snapshot 约束:**不含系统调用或其他非确定性源;单线程执行**。
- 组成部分(四块):
  1. **所有用户可读 CPU 寄存器的初始状态**(含 PC/rip);
  2. **内存映射**及其 r/w/x 权限与对应数据字节;预期引发 page fault 的 snapshot 要求特定页**不被映射**;
  3. **期望终态(可多个)**:若 snapshot 在不同 CPU 微架构上执行不同,则有多个终态;执行引发 CPU 异常时,捕获为对应**信号编号 + 信号地址**;
  4. **元数据**:该 snapshot 如何产生(从程序捕获、多个 snapshot 组合等)。
- 终态判定(§2.5/§3):当前只保留**所有微架构上终态完全一致**的 snapshot(作为对难检非确定性的额外防护);因多终态被丢弃的 snapshot **多达 20%**(§5 Multi-state)。

### 2.3 Player(§2.3)——执行 harness 细节

- 双进程架构:
  - **driver**:有状态的执行编排器;把 snapshot 变换成命令序列、处理执行结果;
  - **harness**:执行 driver 发出的命令,包括运行实际代码;与 driver 隔离 —— harness 中可能崩溃的 snapshot 代码不影响 driver。
- **绑核**:执行**钉在(pinned to)特定核**上;不匹配 ⇒ 该核潜在缺陷。
- 命令协议(NOP snapshot 示例,单条 NOP 放在 0x10000000):
  1. `MapMemory { start = 0x10000000, num_bytes = 4096 }`
  2. `WriteMemory { start = 0x10000000, data = "\x90\xCC\x00 …", num_bytes = 4096 }`
  3. `ProtectMemory { start = 0x10000000, perms = r-x }`
  4. `ExecuteSnapshot { registers = <…, rip = 0x10000000> }`
  5. `ChecksumMemory { start = 0x10000000, num_bytes = 4096 }`
- 关键细节:
  - `\xCC`(x86 INT3 陷阱指令)标记 snapshot 结束;
  - 页内其余字节填零,**保证确定性执行**;
  - 结果 = 寄存器终态 + 内存校验和 vs 期望终态(含信号编号+地址)。

### 2.4 三类代理的具体配置(§2.4)

1. **XED(§2.4.1)**:Intel x86_64 指令编码/解码器;一次最多把 15 字节数据解码为一条 x86_64 指令并报告解码字节数。libFuzzer 集成(Listing 1):`LLVMFuzzerTestOneInput` → `xed_tables_init()` → `xed_decoded_inst_zero()` → `xed_decoded_inst_set_mode(XED_MACHINE_MODE_LONG_64, XED_ADDRESS_WIDTH_64b)` → `xed_decode(&xedd, data, data_len)`。产出 = 最大化 XED 覆盖的字节序列语料(合法+非法 x86_64 指令)⇒ 可能触发 CPU **指令译码器**等组件的有趣行为(附录 B 即例)。
2. **ifuzz(§2.4.2)**:Syzkaller 项目的库;基于 XED 衍生的 x86_64 ISA 模型,提供**生成与变异**两种模式;生成模式只造合法随机指令序列;**无覆盖引导** ⇒ 无限输出、无法择优。用法有二:(a) 从中采样造 snapshot 直接测真机;(b) 作为 fuzz Unicorn 的**字典(dictionary)**。
3. **Unicorn(§2.4.3)**:基于 QEMU 的轻量多平台多架构 CPU 模拟器框架;libFuzzer 挂接方式与 Unicorn 源码树自带的 fuzz target(`fuzz_emu_x86_64.c`,commit 772558119af66269742)类似:把 fuzzer 生成的数据映射到**固定地址**,从**第一个字节**开始模拟执行。libFuzzer 不懂 x86_64 编码,但语料中加入的输入大多是触发 Unicorn 新覆盖的 ⇒ 大多是合法指令序列。

### 2.5 Snapshot 修复与终态记录(§2.4.4)——指令序列 → 合法 snapshot

三阶段:
1. **增删内存映射**:拦截 memory page fault,映射 snapshot 访问的**有限数量**额外页(当前填零);
2. **消除非确定性**:追踪(trace)所有 snapshot 消除全部系统调用;然后在多台机器上**多次重放验证**每个 snapshot 成功且确定;每个 snapshot 默认限时 **3 秒 CPU 时间**;
3. **终态判定**:每个 snapshot 在**所有受支持的 Google 生产平台(微架构)**上运行并捕获每平台终态;当前只保留所有微架构上终态一致的 snapshot。
- **不删除非法指令**:原因 (a) 不在所有 CPU 代上执行就无法判断指令是否非法;(b) 附录 B 展示的缺陷恰好需要非法指令参与。

### 2.6 大规模执行(§2.5)与多核交叉验证判定

- **SiliFuzz checker**:高效跑多 snapshot 的程序,用于生产机后台测试;从磁盘语料读 snapshot、物化进内存、发给每核一个的 player 池。
- **批量与复用**:语料 snapshot 极短,从文件系统读+重新物化的成本相对执行时间高 ⇒ 分批+复用:每批 **50 个随机 snapshot**,用均匀分布从中构造 **1000 次 snapshot 执行**的随机列表;这些数字经验选定,读成本降低 **20×**;多批并发以隐藏 I/O 延迟;列表上的执行用多队列均匀分布到所有可用核。
- **生产机后台测试(§2.5.2)**:Google 数据中心机器持续被一组 SDC 测试筛查(含 SiliFuzz),在**生产使用中**进行;任一时刻每集群只测少数机器以压性能影响;按机器架构定制的概率分布随机选一个测试工具;SiliFuzz 被选中时,作业调度软件**预留 4 个核(2 对超线程对)**、允许运行**最多 2 分钟**;核心数/时限/测试频率按"筛查开销低于机器利用率某百分比"设定;调度软件保证 4 核窗口最终覆盖机器全部核;结果记入机器数据库。
- **缺陷判定(§3)**:只在**同一(些)核上多日可复现同一问题**才判缺陷机;约 **70%** 案例是共享同一物理核的一对逻辑核同坏;大多数其余案例是单逻辑核坏;极少数多核同坏。
- **反馈环/隔离池(§2.6)**:疑似缺陷机下线入隔离池详测(数周,因部分失败依赖频率/电压/温度,需变参数组合重跑);用途:(a) 与其他 SDC 检测工具对比性能;(b) SiliFuzz 版本间回归测试;(c) **用坏机丰富语料**("在一台机上发现缺陷的 snapshot 有较大概率在另一台机上发现缺陷",早期数据支持;此类 snapshot 无视代理覆盖一律保留);(d) 提炼缺陷模式(人工分析共性)。隔离池含可复现 JCC erratum(Intel Jump Conditional Code,[2])的机器 —— 专门构造的 snapshot 能高概率触发该问题,持续可靠地测试 SiliFuzz 基础设施。

## 3. 实验配置(模拟器/硬件、基准、参数)

- 目标:第三方商用 x86_64 CPU(两大厂商,"two major x86_64 vendors",附录 A–D),无 RTL、无厂商内部调试能力,机器视作不透明。
- 语料:Unicorn + XED libFuzzer 语料 + ifuzz 随机 snapshot,**共约 500,000 个**;已部署到 Google 生产集群大部分机器。
- 代理配置:见 §2.4(XED LONG_64 模式;Unicorn 固定地址映射 + 首字节起跳;ifuzz 生成模式 + 字典)。
- snapshot 约束:<100 字节代码、微秒级、无 syscall、单线程、3 秒 CPU 时限、全微架构终态一致。
- 执行调度:每机 4 核(2 HT 对)、≤2 分钟/次、概率抽取、窗口轮转覆盖全核;批 50、批内随机 1000 次执行、读成本降 20×。
- 故障复现标准:同核多日复现。
- 基准对比:与 Google 内部其他 SDC 工具/自动化比较(45% 独有发现);与 ifuzz 纯随机对比(隔离池初步数据)。
- Harpocrates ISCA'24 侧录的 SiliFuzz 配置(供交叉参考):Unicorn 全核 fuzz 40 分钟 → 635,587 输入 → 5 分钟筛 → 173,731 可运行确定性程序(1/3),平均 18.6 指令/程序,≈1,200 可运行指令/秒。

## 4. 实验步骤(可操作流程,编号)

复现 SiliFuzz 最小闭环(x86_64;ARM64 迁移见 §7):

1. **实现 snapshot 格式**:全寄存器初态 + 内存映射(权限+数据)+ 期望终态(可多态:寄存器终态、内存校验和、或信号编号+地址)+ 元数据。
2. **实现 player**:driver/harness 双进程;命令协议 MapMemory/WriteMemory/ProtectMemory/ExecuteSnapshot/ChecksumMemory;结尾陷阱字节(x86 `\xCC`;ARM64 对应 `BRK #0` 之类);页填零;`sched_setaffinity` 绑核;harness 侧信号处理器捕获 SIGILL/SIGSEGV/SIGFPE/SIGTRAP 转换为 (信号号, 地址) 终态。
3. **搭三类代理**:
   a. XED 路径:libFuzzer target 调 xed_decode(LONG_64, 64b addr width);
   b. Unicorn 路径:模拟 Unicorn 源码树 fuzz_emu_x86_64.c 模式,数据映射固定地址、首字节开始执行;libFuzzer 边覆盖反馈;
   c. ifuzz 路径:生成模式随机合法序列;一部分直接转 snapshot,一部分做 Unicorn fuzz 的字典。
4. **snapshot 修复流水线**:fault 拦截补映射页(填零)→ trace 去 syscall → 多机多次重放验确定性(3s CPU 上限)→ 全微架构跑一遍,只留单终态 snapshot。
5. **集群执行**:checker 每批 50、批内均匀随机 1000 次执行、多批并发、队列分派全核;生产模式:概率调度、4 核窗口、≤2 分钟、窗口轮转全核覆盖。
6. **判定与处置**:失配 → 同核复现多日 → 判缺陷;70% 双逻辑核(同物理核)模式作为旁证;入隔离池做频率/电压/温度变参复测。
7. **反馈**:坏机发现的 snapshot 永久保留进语料(无视代理覆盖);定期与内部其他工具对比;版本回归测试。
8. **FCOS 案例复现**(附录 C,详见 §5.5)。

## 5. 实验数据(关键数值 + 图表号)

### 5.1 语料与总体成效(§3)
- 语料 ≈**500,000** snapshot(Unicorn + XED + ifuzz);部署 Google 生产集群大部分机器;检出多台缺陷机。
- 缺陷空间分布:≈**70%** = 共享同一物理核的逻辑核对同坏;其余大多单逻辑核;极少数多核。
- 独有性:≈**45%** 的 SiliFuzz 发现是任何其他可用工具/自动化未曾识别的;部分发现被其他测试独立确认,部分牵连生产事故。
- 时间到失败分布:极宽(有的机器几乎立即失败,有的要数天 CPU 时间才检出第一个缺陷)。

### 5.2 代理对比(隔离池初步数据,§3)
- SiliFuzz 检出的机器中:≈**40%** 只能被 Unicorn+XED 产 snapshot 检出;≈**20%** 只能被 ifuzz 产 snapshot 检出;≈**40%** 两类都能检出 ⇒ 两类 snapshot 高度互补。
- 结论:fuzz 平凡代理(Unicorn/XED)检出的缺陷约为精细生成式 fuzzer(ifuzz)的 **2×**;"fuzzing by proxy" 值得继续投入。
- 归属注意:早期做过三语料交叉授粉(cross-pollination),缺陷 A(Unicorn)、B(XED)、C&D(ifuzz+Unicorn 独立)的归属不保证完全准确。

### 5.3 发现缺陷清单(§3 常见模式 + 附录 A–D)
常见模式(未逐一细分析的众多缺陷中的共性):
- 整数/浮点/向量指令结果错误,**常仅一个 bit 错**;
- 假 SIGFPE/SIGSEGV/SIGILL;
- 缺失浮点异常;
- 该 SIGILL 处未 raise SIGILL;
- **粘滞标志位**(EFLAGS 或类似状态寄存器某 bit 恒置位,无视底层条件);
- REP(NE) 前缀串指令**欠执行**(undershooting);
- 浮点数据指针寄存器(RDP)值失配。
- 相关性观察:最常发现的缺陷类型与 Unicorn 中**以 C 代码实现**的部分(浮点、向量指令等,相对 JIT 编译部分)相关 —— 方法对 C 代码部分覆盖反馈更好。
- 四组详析缺陷:
  - **缺陷 A(附录 A):F2XM1** —— x87 指令 2^x−1 偶发错误结果;最小化:只剩 F2XM1 本身(输入来自 FLDLN2 还是内存无关);同一物理核上错误结果恒定、跨受影响核不同;厂商诊断工具确认;类似 Meta(Dixit et al.)报告但未知是否同一;**Unicorn 产 snapshot 发现**;
  - **缺陷 B(附录 B):非法指令过冲(overshoot)** —— 不兼容前缀+指令应 #UD,却有时越过且不 raise;来自 fuzz XED(所以含非法指令);技术上违规但生产代码无非法指令故无实害;**XED 产 snapshot 发现**;
  - **缺陷 C(附录 C):FCOS 误算**(详见 §5.5);**ifuzz 与 Unicorn 产 snapshot 独立发现**;
  - **缺陷 D(附录 D):x87 数据指针漏更新** —— FISTTPLL 应设数据指针为存储地址,却有时置零;只影响数据指针、不影响其他错误寄存器;仅特定核对上出现;**ifuzz 与 Unicorn 独立发现**。

### 5.4 执行工程数据(§2.5)
- 批大小 50 / 每批 1000 次执行 / 读成本降 **20×**;生产测试:4 核、≤2 分钟。
- 多终态丢弃率:最高 **20%**(§5 Multi-state)。

### 5.5 FCOS 案例完整复现(附录 C + Figure 1)——逐步
- **复现代码(Listing 3)**:
  ```
  // Prologue(序)
  fldln2        // st0 = ln(2)
  fldln2        // st0 = ln(2), st1 = ln(2)
  fprem1        // st0 = partial remainder(st0/st1)
  // Payload(载荷)
  fld1           // st0 = 1.0
  fcos           // st0 = cos(1.0)
  ```
- **期望值**:cos(1) = 0.5403023059(二进制 **0x3fe14a280fb5068c**);
- **实际错误值**:0.5403023043(二进制 **0x3fe14a280edd9be7**);差 <0.0000003%;错误值对共享物理核的两个逻辑核一致。
- **隐藏状态/记忆效应**:序把核置于"坏状态",载荷开始误算;序与载荷可**同进程或不同进程**执行(跨进程仍触发);CPU 在未知时间后自行恢复;**不用序也能触发** —— 载荷循环跑、ST(0) 换不同值,若干次迭代后开始误算。
- **输入映射(Figure 1)**:x 轴 = COS 参数,y 轴 = 误算时为 X、否则 0;理论:**输入二进制编码的 bit 23(1<<23)触发** —— 该位置 1 时计算正常、清 0 时受影响核几乎普遍误算。
- **复现步骤(从上述内容整理)**:
  1. 写 prologue+payload 汇编,固定跑在单核(pin);
  2. 期望值硬编码 0x3fe14a280fb5068c,比对实际;
  3. 验证跨逻辑核(同物理核对)一致性;
  4. 变体 1:拆 prologue 与 payload 到两个进程;
  5. 变体 2:去掉 prologue,循环 payload 并扫 ST(0) 输入值;
  6. 按图 1 扫输入空间,验证 bit-23 假设(置位/清零对比)。
- 该案例是"**边际缺陷 + 隐藏微架构状态 + 数据依赖(单 bit)**"三要素的范本,与 SDCShield 的 VA[55:48] 瞬态/数据位依赖故障(cn23154 NUMA3 案例)同构,方法论(单核锚定、输入位扫描、跨进程状态保持)可直接迁移。

## 6. 实验结论(编号列出)

1. fuzzing by proxy 可行且已产实效:平凡代理(Unicorn/XED)比精细生成式 fuzzer(ifuzz)多检 ≈2× 缺陷(40% vs 20% 独有检出),两类高度互补。
2. 语料规模可控(<100 字节/snapshot)即足够触发真缺陷;约 45% 发现为独有,证明代理覆盖与硬件缺陷的相关性非平凡。
3. 缺陷物理局部性:≈70% 为同物理核对同坏 —— 电气缺陷多局限于单物理核,支持"逐物理核筛查"的调度设计。
4. 真实 CPU 缺陷存在"隐藏状态/记忆"(FCOS 案例:跨进程、自恢复),单条指令最小化不总是充分(FCOS 需 prologue 或迭代预热)。
5. 缺陷模式集中在:单 bit 结果错、假/缺信号、粘滞标志位、串指令欠执行、x87 指针寄存器 —— 与代理(Unicorn C 实现)的覆盖反馈强弱相关。
6. 代码覆盖是弱质量指标(自认):100% 边覆盖也不保证检全软件 bug,对硬件保证更少;理想是直接从硬件收集覆盖,但 CPU 对用户基本不透明。
7. 多终态 snapshot 被丢弃高达 20%,其中可能混有"有意义的微架构差异" —— 静态分析区分非确定性与真差异是改进方向。
8. 差分测试范式确立:跨核/跨机交叉验证 + 多日复现 = 判定标准,无需 RTL 与厂商工具。

## 7. 复现要点(ARM64 复现最小版本)

### 7.1 可直接复用
- **开源仓库**:github.com/google/silifuzz(公开;Harpocrates 两文均引此仓库;现代版本**已支持 aarch64**)—— snapshot 格式、player、词料生成流水线可直接取用,是三篇中唯一有官方开源实现的。
- **snapshot 格式设计**:寄存器初态 + 内存映射(权限/数据)+ 期望终态 + 元数据;信号即终态((信号号, 地址));页填零保确定性。ISA 无关,直接可用。
- **player 双进程隔离 + 命令协议**:driver/harness 分离、MapMemory/WriteMemory/ProtectMemory/ExecuteSnapshot/ChecksumMemory 五命令 —— 原样可移植。
- **绑核 + 逐核判定 + 同物理核对(70%)旁证**:ARM64 无 SMT(一般)则退化为"单核锚定";SDCShield 的 cluster_anchored_logs 基础设施已具备同款能力。
- **调度工程参数**:批 50 / 1000 次执行 / 20× 读成本摊销;4 核窗口、≤2 分钟、概率调度 —— 数据中心筛查的现成经验值。
- **判定标准**:多日同核复现才算缺陷 —— 直接采纳,抑制假阳性。
- **坏机反馈语料**:坏机 snapshot 永久入语料 —— SDCShield 可同款维护"激发缺陷的测试用例库"。
- **三要素代理思想**:编码器/模拟器/生成器三类代理互补(40/20/40)—— ARM64 对应:Capstone/LLVM MC(反汇编)≈XED;QEMU/Unicorn aarch64≈Unicorn;自研 ISA 模型生成器≈ifuzz。
- **陷阱标记**:x86 `\xCC` → ARM64 用 `BRK #imm`(SIGTRAP)或 `UDF`(SIGILL)标记 snapshot 结束;页内填零同款。
- **FCOS 案例的复现方法论**:序-载荷结构、跨进程状态、输入位扫描(bit-23 类)、同物理核一致性 —— 与 cn23154 VA-path 故障的复现方法直接同构(见 memory: ld1rd/stnt1d 栈重装载触发)。

### 7.2 需替代/不可行
- **x87 栈机指令**(F2XM1/FCOS/FPREM1/FISTTLL):ARM64 无 x87 —— 对应物是 NEON/SVE 超越函数(SLEEF 生成代码)与 FPCR/累加器状态;附录 A/C/D 的具体缺陷不可在 ARM64 上复现,但其**模式**(超越函数数据依赖、状态寄存器漏更新)可映射:SLEEF sleef_neon/sleef_sve 测试 + FPCR sticky flag 检查。
- **REP(NE) 串指令欠执行**:x86 特有;ARM64 对应 LDNM/STNM(SVE 非临时访问)或 LDP/STP 多种宽度遍历。
- **EFLAGS 粘滞标志**:对应 ARM64 NZCV/FPCR 标志(IOC/IXC/UFC/OFC/DZC 粘滞位)—— 反而更规整,可做系统性检查。
- **Google 生产集群与隔离池**:不可复现(私有基础设施);复现上限是单机/小集群 + 人为"变频率/电压/温度"(openEuler/Kunpeng 上无 cpufreq,需用现有降频约束的替代方案)。
- **"所有受支持 Google 生产平台跑终态"**:复现改为"所有手头 ARM64 微架构(如 Kunpeng 920 + 其他 ARMv8.x)终态一致"。
- **libFuzzer 覆盖反馈对 QEMU TCG(JIT 代码)弱**的坑(§3/§5):Unicorn/QEMU 中 JIT 部分覆盖反馈差 —— ARM64 复现若用 QEMU TCG 代理会重蹈,宜改用 QEMU 的 TCI 解释模式或硬件辅助代理。

## 9. 局限与坑

1. **非学术报告**:作者自认 work-in-progress、"不声称学术新颖性"、未与其他相似系统对比(无渠道);无评审版本;引用其数字时注意口径(隔离池数据是"preliminary")。
2. **代理覆盖与硬件缺陷的因果链是假设**:"代理覆盖好 ⇒ 触发有趣 CPU 行为"是 conjecture(§2.1 原文承认);作者自己列"更好覆盖指标"为最大挑战(quality)。
3. **无定量检出率/覆盖率曲线**:全文没有 gem5 式的故障注入定量(与 Harpocrates 互补:一个有定量无真机,一个有真机无定量);45%/40%/20%/70% 都是 fleet 运营统计,非受控实验。
4. **多终态丢 20%**:丢弃策略保守,可能丢掉真正有意义的微架构差异(甚至 bug);静态区分技术未实现。
5. **短测式的天然盲区**(作者自认 + Harpocities Micro'26 前缀实验印证):<100 字节、微秒级 snapshot 难以覆盖大位阵列(L1D/IRF)瞬态故障与需要长时状态的边际缺陷;FCOS 案例靠 prologue/迭代"凑"出了状态,纯随机很难系统性命中。
6. **x86_64-only(2021 版)**:设计 ISA 无关,但论文实验全 x86;ARM64 支持是开源仓库后续演化的(复现时以仓库现状为准,论文未覆盖)。
7. **缺陷归属不确定**:三语料早期交叉授 pollination,A/B/C/D 的代理归属"cannot guarantee with certainty"。
8. **"illegal instructions 不删除"是双刃剑**:保住了缺陷 B,但也使语料含大量真非法指令,依赖"所有微架构终态一致"兜底;ARM64 上 UNDEFINED 编码空间更规整,策略需重评估。
9. **时敏缺陷的调度代价**:time-to-failure 分布极宽(数天 CPU 时间)⇒ 4 核/2 分钟的抽查预算下,慢故障漏检风险未量化。
10. **与 SDCShield 场景的差异**:SiliFuzz 面向"健康集群中筛出极少数缺陷机"(DPPM 级);SDCShield/激发实验面向"单机深检 + 复现机理"—— 前者要防假阳性(多日复现),后者要提灵敏度,直接照搬判定标准会过保守。

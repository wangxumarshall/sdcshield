## 1. 研究问题与核心贡献(≤5 行)

首个对**生产环境超大规模 CPU 群体**(阿里云 100 万+ 处理器、28 数据中心、14 国、2017 年起部署)中 SDC 的定量系统研究,历时 32 个月(§1 贡献列表)。核心产出:12 条编号 Observation(§3–§6),覆盖失败率统计、脆弱特性归类(计算型 19 颗 vs 一致性型 8 颗)、bitflip 位置规律(浮点集中在尾数段)、复现性与温度触发关系(lg(频率) 与温度线性相关)。并提出缓解工具 Farron(testcase 优先级 + 温度控制),一轮常规测试 1.02 小时 vs 基线 10.55 小时(§7.2)。

贡献五分法(§1 原文列举,复现时可直接对位):

1. 大规模生产环境 SDC 评估(100 万+ CPU、32 个月;失败率总体统计 + 微架构/测试时机/单核 vs 全核影响);
2. SDC 的软件影响调查(脆弱特性识别:cache 一致性、浮点计算、向量计算;现有失效模型的缺陷——浮点 SDC 多翻尾数位、精度损失小,使基于精度的检测失效);
3. SDC 复现性分析(高复现 SDC 会频繁显影于生产;低复现 SDC 依赖特定条件——温度、负载压力);
4. 现有缓解实践评估(testcase 优先级化设计空间 + 多线程场景测试缺口);
5. 具体缓解方案 Farron(常规测试 + 优先级 + 温控,检测率与开销双优)。

## 2. 实验方法(测试程序形态、检测机制、输入生成、循环结构)

### 2.1 工具链组织:633 个 testcase + 1 个框架(§2.3)

- 工具链由**芯片制造商提供**(未公开,论文明确 "our toolchain is not publicly available",§6.1),面向云负载相关 SDC 检测,共 **633 个 testcase + 1 个框架**。
- 框架职责:按用户规格选择要执行的 testcase、控制执行顺序、资源分配(CPU 时间与并发度)(§2.3)。
- testcase 形态 = "模拟云负载的程序",同时考虑**软件行为与硬件特性**设计。**大多数 testcase 针对单一处理器特性**:浮点计算、分支预测、cache、核间互连等(§2.3)。
- 复杂度分三档(§2.3 原文列举):
  1. **在循环内反复执行一条特定指令**;
  2. **调用库函数**;
  3. **调用应用逻辑**。
- 补充验证:作者另用 OpenDCDiag 作为补充工具链,"reach the same observations"(§2.3);SiliFuzz 未试用(§6.1)。
- testcase 长度(循环次数)**可配置**,触发概率依赖长度——因此复现性度量采用"每分钟错误数"(occurrence frequency)而非每次运行错误率(§5 开头)。

### 2.2 检测机制与判定

- 框架驱动 testcase 执行并检查 SDC 发生(§2.3)。
- **根因判定流程**:测试失败 ≠ CPU SDC(可能是内存错误等)。若合理努力内无法定位根因,将可疑处理器**寄回制造商**;论文报告的所有坏 CPU 均经制造商确认(§2.3)。
- 工具链不完整:确实存在该工具链检测不出的 SDC(§2.3),研究为 best-effort,假阳/假阴都可能。
- 一轮大规模测试 = 顺序执行全部 633 个 testcase,**每个 testcase 分配管理员指定的相等测试时长**(§2.4)。

### 2.3 深度实验:27 颗坏 CPU(§2.4 末段)

- 数百颗坏 CPU 中,27 颗留下做深度实验(其余已退回制造商)。累计 **数千万次(tens of millions)测试**,采集 **1 万余条 SDC 记录**(§2.4)。
- 复现性协议(§5):对每个失败 setting(= testcase × 处理器组合)反复运行失败 testcase,记录 occurrence frequency(错误/分钟),按 setting 分别记录。
- 指令归因(§4.1):工具链对部分错误保存上下文并指出错误指令;对不可复现错误,改用**统计法——用 Pin 动态插桩统计每个 testcase 中各类型指令的执行次数**,缩小嫌疑指令范围(例:FPU1/FPU2 中嫌疑指令为一条用浮点特性算 arctangent 复杂数学函数的指令;CNST2 嫌疑为管理事务区间的指令;CNST1 的 cache 一致性问题无法定位到指令)。
- 注意:**使用了缺陷指令的 testcase 不一定报错**——MIX1 中一条缺陷指令出现在 7 个 testcase 中,只有 2 个产生错误(§4.1)。

### 2.4 bitflip / 精度分析(§4.2)

- bitflip 位置 = 期望结果与实际结果的**逐位异或 mask**;若某 setting 超过 5% 的 SDC 记录有相同 mask,则该 mask 记为一个 bitflip pattern(§4.2,Observation 8 定义)。一个 setting 可有多个 pattern。
- 精度损失 = 期望数据与实际数据的相对精度损失,按数据类型分别做 CDF(Figure 4(e)-(h))。
- 一致性型 SDC **不参与** bitflip 分析(无确定性模式,§4.2 开头)。

### 2.5 温度实验方法(§5,Observation 10)——重点

- **测温**:执行 testcase 期间,通过"reading cooling device monitor data from system kernel file"(读内核 cooling device 监控数据,即 /sys 中降温设备侧数据)监测处理器温度(§5)。注意:**不是** thermal_zone 温度(该板无 CPU thermal zone 的经验与本文互相印证)。
- **加热方式(两类 setting 两类处理)**(§5):
  1. 自然到温:部分 setting 负载本身可逼近处理器工作温度上限,直接采集不同温度下的执行信息;
  2. **预热**:对自然到不了高温的 setting,测试前用压力工具链(如 Linux `stress` 命令行工具)把处理器预热到目标温度再测。
- **相关性计算**:对 SDC occurrence frequency 取以 10 为底对数,对核温做**最小二乘线性拟合**;27 颗处理器中 **6 颗**呈线性依赖,Pearson 相关系数 > 0.75 → 证实温度与发生频率的**指数关系**(§5,Figure 8)。
- **温度与压力解耦实验**(§5 末):为分离温度与指令使用压力(instruction usage stress)的影响——在**非受测核**上跑 stress 工具链,同时在目标核上跑测试负载。热量主要由 stress 侧产生、由散热设备耗散,受测负载对温度影响很小 → 在温度几乎不变的情况下提高 CPU 利用率,观察到**高 CPU 利用率下 SDC 发生频率更高**(证明指令使用压力本身也是触发条件)。
- 最小触发温度:某些 setting 存在温度阈值——MIX1 的 testcase C 所有 SDC 记录温度 > 59℃(空闲约 45℃);阈值以下连续测**数天**无错误(§5)。
- **三个反直觉案例**(§5,温度归因的铁证,复现时可作为方法论叙事模板):
  1. **他核行为**:某缺陷核只有**其他核忙**时才出错,频率随忙核数增加而升——但缺陷部件并不在核间共享;根因是核共享散热设备,他核忙 → 缺陷核温度更高。
  2. **余热**:某坏 CPU 的错误依赖测试顺序——testcase X 先跑、Y 后跑则 Y 出错;X 单独跑 Y 或反序则不出。X 对 CPU 施加巨大压力产生大量余热,使 Y 在"单跑 Y 达不到的温度"下被测。
  3. **工具链更新**:换用更高版本检测工具链后,某坏 CPU 的 SDC 发生频率**下降**——测试逻辑与配置都没变;根因是新框架更高效、发热减少。

### 2.6 生产案例(§2.2,深读价值:三类根因各一例)

三个真实生产事故,每例都是一种 SDC 类型的活样本:

1. **存储应用校验和错配** → 数周调试定位到某颗 CPU 上"一条与校验和计算相关的指令**间歇性**给出错误结果"(单缺陷指令、间歇性 = 计算型典型);
2. **校验和错配(不同根因)** → 客户端线程把数据+校验和打包进 buffer 共享给 daemon 线程,**cache 一致性缺陷**使 daemon 时常读到不一致数据(一致性型典型);
3. **断言失败** → 应用用 hash map 管理元数据,坏 CPU 的**哈希计算缺陷**破坏元数据服务(计算型 × 数据结构放大)。

MetS/Google 对照(§1):Google Cloud "少量处理器执行罕用指令出错,使大规模数据分析应用给出错误答案";Meta "一台机器因错误计算把文件大小误判为 0,导致数据库丢文件";Meta 案例调试耗时**数月**,阿里云曾花**数周**——SDC 调试成本背景论据。

### 2.7 Farron(§7,提出的方法,非本文重点但为实验一部分)

- 三状态工作流:pre-production / online / suspected(Figure 10)。pre-production 状态做资源充足的全面测试 → 进入 reliable resource pool;online 状态下用户应用跑在已证可靠核上,受 triggering condition controller 约束,定期常规测试;测试失败转 suspected 状态做定向深测 + 依据结果调整可靠资源。
- 自适应温度边界(§7.1):窗口跟踪近期温度记录,超半数超界 → 上调 workload backoff 边界(自学习当前场景正常工作温度);低于半数超界 → 触发 backoff 直到温度回落。常规测试时长也随边界自适应(低边界 = 更短测试)。
- testcase 三级优先级(§7.1):basic(设计针对某特性但在大规模测试中从未检出)/ active(有成功检出史)/ suspected(当前处理器核上检出过)。主要把测试资源分给"受保护应用用到的特性"的 suspected(若有)与 active 测试;其余 best-effort。
- 测试环境强化(§7.1):测试先行 burn-in 负载、处理器所有核同时测试以升温(基于 Obs.10:高温下才现形的 SDC 才能被常规测试覆盖;工具链 testcase 本身有压力、能发热,可覆盖应用执行温度)。
- 细粒度下线(§7.1):对已检出缺陷核,累计 suspected 测试用例做充分测试,高效验证其余核是否完好;**若一颗处理器检出 > 2 个缺陷核则整颗下线**(贴合 Obs.4 中多缺陷核现象);否则只屏蔽缺陷核、其余核继续服役(引 Hyrax, OSDI'23)。

## 4. 实验步骤(可操作流程)

大规模筛查(机队级,§2.4):
1. 出厂交付后执行预生产测试(全 633 testcase,顺序,等时长);
2. 数据中心交付后再次预生产测试;
3. 重装系统后第三次预生产测试;
4. 生产期按组常规测试(每组约 2 周,全机队数月一轮,基线每 3 个月一轮);
5. 失败 CPU:尽力定位根因(排除内存错误等),无法定位则寄回制造商确认;确认坏 CPU 退回厂商或(留样)进入深度实验。

深度实验(单颗坏 CPU 级,§4–§5):
6. 记录该 CPU 的 arch / 机龄 / 缺陷物理核数 / 失败 testcase 数 / SDC 类型 / 受影响负载与数据类型(如表 3 格式);
7. 对每个失败 setting 反复运行失败 testcase,统计 occurrence frequency(错误/分钟);
8. bitflip 分析:收集每条 SDC 记录的 XOR mask,统计 bitflip 方向(0→1 / 1→0)、按数据类型的位分布(Fig 4(a)-(d))、精度损失 CDF(Fig 4(e)-(h))、pattern 占比(>5% 判 pattern,Fig 6)、每 pattern 翻转位数分布(Fig 7);
9. 指令归因:Pin 插桩统计每个 testcase 各类指令执行次数,与失败/通过 testcase 集合对齐,锁定嫌疑指令;
10. 温度实验:测温(内核 cooling device)→ 自然到温 setting 直接采数;低温 setting 用 `stress` 预热到目标温度再测;lg(frequency) vs 温度最小二乘拟合 + Pearson;
11. 温度/压力解耦:非受测核跑 stress、受测核跑测试负载,固定温度变利用率;
12. (论文)将观察转化为 Farron 策略并在坏 CPU 上评估覆盖率与开销。

### 5.5 bitflip 与精度损失(Observation 7/8,Figure 4–7)

- **51.08%** 的 bitflip 为 0→1(整体无方向偏好);MIX1 的 16 位整数中 **72.27%** 为 0→1(§4.2)。
- 精度损失(Figure 4(e)-(h)):
  - 80 位扩展双精度(float64x):全部 < **0.002%**;
  - 64 位双精度:99.9% < **0.02%**;
  - 32 位单精度:80.25% < **5%**;
  - 32 位整数:**40.2%** 的精度损失 > **100%**。
- bitflip 多位于数表示的中部、向两端递减;浮点尾数段最长故集中于此;最高有效位翻转罕见(Observation 7)。
- bitflip pattern(同 setting 固定位置翻转)在不少 setting 中占比极高(Figure 6 矩阵,色标 0.000–0.9600,多格 0.83–0.96,部分为 0)。
- 每 pattern 翻转位数分布(Figure 7):float32 1 位 98%/2 位 2%;float64 0.90/0.08/0.02(1/2/>2 位);float64x 0.72/0.20/0.08;int32 0.91/0.09;bin8 0.96/0.04。→ **多位翻转可观存在**,挑战"多位翻转罕见"的传统故障模型。

### 5.6 复现性(Observation 9,§5)

- occurrence frequency 范围 **0.01 次/分钟 ~ 数百次/分钟**;**51.2%** 的 setting > 1 次/分钟。
- 生产案例:一颗坏 CPU 导致某服务在约 **4.5 小时**内误报 **26 次** invalid-data 错误。

### 5.7 温度相关性(Observation 10,Figure 8/9,§5)

| Setting | 温度区间(℃) | 频率范围(对数轴) | Pearson r |
|---|---|---|---|
| MIX1, pcore0, testcase C(Fig 8a) | 66–76 | 0.001–0.1 次/分钟 | **0.7903** |
| MIX2, pcore1, testcase C(Fig 8b) | 56–68 | 0.01–1 次/分钟 | **0.9243** |
| FPU2, pcore8, testcase L(Fig 8c) | 48–56 | 0.4–4 次/分钟 | **0.8855** |

- 27 颗中 6 颗呈 lg(频率)-温度线性;MIX1 testcase C 阈值 59℃(空闲 ~45℃),阈值下测数天无错误。注意 8(a) 的频率绝对值极低(0.001–0.1 次/分钟)——低温下接近不可复现,升温后数量级抬升。
- 最小触发温度 vs 该温度下发生频率(Figure 9,温度轴 40–75℃,频率轴 0.001–100 次/分钟,每点一个 SDC setting):lg(频率) 与最小触发温度线性拟合 **Pearson = −0.8272** → 温度边界越高,频率越低,据此把 SDC 分为 apparent(低温高频,宜测试)与 tricky(高温低频,宜温度控制)。tricky SDC 若纯靠测试覆盖,需要对**所有** CPU(未知谁有 tricky SDC)长时间维持高温测试——损伤处理器健康且低效,故转温控策略。

## 6. 实验结论(编号)

1. (Obs.1) 总体 **3.61‱**(约 1/2770)的 CPU 引发 SDC,SDC 是普遍问题而非黑天鹅。
2. (Obs.2) 预生产检出 3.262‱(占 90.36%),常规测试 0.348‱——预生产测试不可省,且仍有漏网。
3. (Obs.3) 所有微架构均有坏 CPU(0.082–9.29‱),失败率不随新芯片下降。
4. (Obs.4) 缺陷可只影响单物理核(约一半)或全核;同型全核缺陷各核频率差可达数量级;多缺陷核比例高于 Google 报告。
5. (Obs.5) 五大脆弱特性:ALU/向量/浮点/cache 一致性/事务内存;两类 SDC:计算型(19)与一致性型(8),一致性型**只能靠多线程测试**检出。
6. (Obs.6) 全部数据类型受影响,浮点最脆弱。
7. (Obs.7) 浮点 bitflip 集中于尾数段,精度损失小(float64 99.9% < 0.02%)——削弱现有基于精度的检测。(**注意**:该"尾数论"被同目录 SEVI(ASPLOS 2026)的机队数据推翻/修正,引用时需谨慎,见 §9。)
8. (Obs.8) 同 setting 的 bitflip 倾向固定位置(pattern),多位翻转可观;挑战 IID 单比特故障模型。
9. (Obs.9) 51.2% 的 setting 频率 > 1 次/分钟,高复现 SDC 生产影响大。
10. (Obs.10) 温度是重要触发条件:lg(频率) 与温度线性(6/27 颗,r>0.75);存在最小触发温度阈值(如 59℃);温度与指令压力是两个独立触发条件;工具链版本更高效→发热降低→频率下降(三个反直觉案例:他核忙/余热/工具链更新,§5)。
11. (Obs.11) 633 testcase 中 560 个在实际机队无效 → 测试优先级化空间大;多线程冲突场景是现有工具链盲区。
12. (Obs.12) 校验和/ECC/EC/冗余/预测等现有容错技术对 CPU SDC 有效性受损(CRC/EC 重度使用向量运算,自身即脆弱;SDC 可发生在校验和计算之前;ECC 只纠单比特)。
13. (§7) Farron:优先级 + 温度控制 + 细粒度下线,一轮 1.02h、开销 0.017%–0.145%,覆盖率与开销均优于基线。

## 7. 复现要点(ARM64 单机/小集群最小可行版本)

### 7.0 最小可行实验包(推荐给 SDCShield 的三个立即动作)

1. **"setting 级复现性档案"实验**:对 cn23154 已知故障,把 SDCShield 跑成 SOSP23 协议——每个 (test, core) 组合反复运行、记录 occurrence frequency(错误/分钟)、产出温度扫描曲线(stress 预热 + cooling_device 读数 + lg-freq 线性拟合 + Pearson)。单机即可执行,直接对标 Fig.8 三行数据。
2. **bitflip mask 流水线**:失败现场字部落盘 → XOR mask 聚合 → pattern 判定(>5%)/方向比(0→1 占比)/位数分布/精度损失 CDF——对标 Fig.4/6/7 的全套统计输出。
3. **计算型/一致性型判别实验**:同一故障机上跑 SDCShield 的单线程计算测试(FMA/SVE/eigen)与多线程一致性测试(mesh/spinlock/atomic/lock),按"只有多线程测试能检出 → 一致性型"判别——对标其 19:8 分型方法。

### 7.0.1 术语对照表(SOSP23 → SDCShield 概念映射)

| SOSP23 概念 | SDCShield 对应物 |
|---|---|
| testcase(厂商工具链 633 个) | 注册测试 279 个(PROD 质量)+ 新激发实验 |
| setting(testcase × 处理器) | (test, cpu) 组合——框架已按核报告失败 |
| occurrence frequency(错误/分钟) | 失败计数 / 运行时长(需新增:失败时落盘计数,离线聚合) |
| 常规测试(每 3 个月、每组 2 周) | 离线全量轮询(-t 时长 × 全测试) |
| cooling device 温度读数 | /sys/class/thermal/cooling_device*(Kunpeng 920 可用) |
| stress 预热 | stress-ng / SDCShield 自身高压测试跑非受测核 |
| 厂商根因确认 | 不可得;替代 = cn23154 已知故障 + 复现协议内证 |

### 7.1 可直接复用

- **测试形态三分法**(单指令循环 / 库函数 / 应用逻辑)与"每 testcase 等时长顺序执行"的协议——SDCShield 的 TEST_LOOP + `-t` 时长模型天然对应;fork-per-test + 每核 worker 线程即其"resource allocation"。
- **occurrence frequency(错误/分钟,按 setting 记录)度量**——比"每轮是否失败"细一个量级,可直接在 SDCShield 失败日志上按 (test, cpu) 聚合实现。
- **bitflip mask 统计流水线**:XOR mask → >5% 同 mask 判 pattern → 方向(0→1/1→0)/位置分布/位数分布/精度损失 CDF。SDCShield 已有 memcmp_or_fail,只需把失败现场的实际字节落盘即可离线分析。数据类型矩阵 i16/i32/ui32/f32/f64/bit/byte/bin16/32/64 可作为新测试的输出类型清单。
- **温度实验三件套**:内核 cooling device 读数(项目经验:Kunpeng 920 无 cpufreq、无 CPU thermal_zone,只有 cooling_device——与本文读 cooling device 的做法恰好对齐)、`stress` 预热、lg(freq) vs 温度最小二乘 + Pearson。单机即可复现协议(样本量另说)。
- **温度/压力解耦协议**:非受测核跑 stress + 受测核跑测试——在 SDCShield 上就是"压核组 + 被测核组"的调度,框架级可支持(`-n`/affinity)。
- **OpenDCDiag 等价验证**:本文已声明 OpenDCDiag 能得出相同观察——SDCShield 作为其分支,天然可承接该定位;633-testcase 工具链不可得,但 SDCShield 279 个注册测试可作为对应物。
- **Pin 指令计数归因**:ARM64 上可用 perf stat(even: instructions by opcode 类)或 QEMU 插桩替代思路(见右栏)。

### 7.2 需替代/不可行

- **100 万 CPU 机队、28 数据中心、32 个月**:不可行;单机/小集群只能复现"深度实验"层(对已知坏 CPU 的协议),不能复现失败率统计层。3.61‱ 意味着 1 万颗 CPU 才期望 ~3.6 颗坏 CPU。
- **厂商确认坏 CPU**:不可行;只能用 cn23154(NUMA3 VA-path 故障机)等自有机型做"已知故障样本"。
- **633 厂商 testcase**:不可得(未公开);需以 SDCShield 测试集 + 自研激发实验替代——这恰是对比叙事的机会:用"我们 279 个测试 + 新激发设计"对标其"633 个中 560 个无效"的效率论据。
- **Pin(IA-32 only)**:需替代——ARM64 用 perf/插桩或直接在测试内嵌指令计数;或用 SDCShield 的崩溃上下文框架(--on-crash=context)。
- **事务内存特性**:ARM64 无 x86 TSX 对应物;一致性型实验应以原子指令/独占访问(ldxr/stxr)、cache 一致性(mesh/memcpy 系列已有)替代。
- **Farron 温控(cooling device 控制)**:项目经验该板 cpufreq/温控不可写;只能做 workload backoff 侧。
- **重装系统时点的失败率分桶**(2.306‱):单机复现无意义,只作引用数据。

## 8. 作为对比基线的价值(可测对比轴 + 论文基线数值)

1. **测试效率轴**:论文基线 = 633 testcase / 560 无效(88.5% 无检出)/ 一轮常规测试 10.55 小时(等时长顺序执行)。SDCShield 新实验可对比:"单位检测时长内检出的独立缺陷 setting 数"、"每 testcase 的历史检出贡献",论证优先级/激发设计的增益(对标 Farron 的 1.02h 与 0.017–0.145% 开销)。
2. **计算型 vs 一致性型覆盖轴**:论文基线 = 19:8 的缺陷构成、一致性型只能多线程检出、多线程冲突场景是厂商工具链盲区。SDCShield 若有强多线程一致性激发测试(锁/原子/mesh),即针对其声明的盲区——这是"更优"论证的最硬角度之一。
3. **FMA/向量轴**:论文 SIMD1 案例为"乘加同拍的向量指令"出错;结合 Veritas 机队数据(向量单元 SDC 率高出标量 2–3 个数量级),NEON/SVE FMA 激发强度是直接对标轴。
4. **温度敏感性轴**:论文基线 = lg(freq)-温度线性 r=0.7903/0.9243/0.8855、最小触发温度 59℃、Pearson(最小触发温度, lg 频率)=−0.8272。SDCShield 可报告同协议下的 r 值与温度阈值,证明(或证伪)新实验在温度激发维度等效或更敏感。
5. **bitflip 统计轴**:论文基线 = 51.08% 0→1;float64 99.9% 精度损失 < 0.02%;int32 40.2% > 100%;pattern 占比最高 ~0.96。SDCShield 失败记录可产出同格式分布图,直接逐项对齐(注意 SEVI 已修正尾数论,对比时引用两边)。
6. **复现性轴**:论文基线 = 0.01–数百次/分钟、51.2% setting > 1 次/分钟。可对比新实验在(注入的或真实的)已知故障上的激发频率,论证"更易触发/更快检出"。
7. **预生产 vs 常规检出占比轴**:论文基线 = 预生产 3.262‱(占 90.36%,其中重装系统时点 2.306‱ 独大)/ 常规 0.348‱。含义:下线后重装系统的高压测试窗口是最大检出贡献者(可能因重装后机器空载、可全速全核跑满)。SDCShield 若设计"裸机/重装后高强度一轮",可直接对标该窗口的效率论证。
8. **重装时点独大现象**:2.306‱ vs 出厂 0.776‱ / 数据中心交付 0.18‱——三次预生产测试中重装后检出最多,暗示交付链中的测试覆盖不足 + 高压测试窗口价值;ARM64 侧可类比"新部署前压测一轮"的运维协议设计。

## 9. 局限与坑

- **"重装系统后检出最多"的解释不确定**:2.306‱ 的机理(真缺陷在用了一段时间后显化 vs 单纯重装后测试条件更纯净)论文未做归因实验区分——若引用其论证"机器服役早期就该高压测试",逻辑链不完整(与 ASPLOS24 Vega 的老化论结合才能闭环)。
- **Farron 评估样本即深度实验样本**:Farron 覆盖率/开销评估只在 Table 3 列出的 6 颗坏 CPU 上做(Figure 11/Table 4),样本小且与开发观察同源,存在过拟合叙事风险。
- **工具链黑箱**:633 testcase 的具体内容、输入生成方式、检测判据全部未公开;复现只能"协议级"等价,不可能"内容级"等价。论文自己也承认工具链不完整(有检不出的 SDC)。
- **统计口径陷阱**:3.61‱ 是"被该工具链检出并被厂商确认"的比率,严重依赖工具链能力;不同工具链不可直接比数字(论文 Obs.4 中与 Google 多缺陷核比例的差异即由此而来)。
- **尾数论的后续修正**:Obs.7(浮点 SDC 只损尾数、精度损失小)被 SEVI(ASPLOS 2026,同 ref 目录)的机队实测推翻/修正——写论文引用 SOSP23 该条时必须同时引用 SEVI,否则立论会被审稿人击穿。
- **温度测量的间接性**:读 cooling device 而非直接核温;且"温度"与"指令压力"高度相关,论文虽做了解耦实验,但 6/27 颗才有显著线性——温度相关性是少数现象,不是普适规律,复现时样本量要留余量。
- **深度实验样本选择偏差**:27 颗 = 没被退回厂商的子集,可能偏向"更难定位/更复现不了"的样本,19/8 的类型比例不一定代表全体数百颗的构成。
- **失败 setting 定义耦合 testcase 长度**:occurrence frequency 依赖循环长度配置(§5 开头明说),跨论文对比时若时长/循环数不同,频率不可直接比,需归一化到"每指令/每分钟"。
- **不可复现的环境条件**:阿里云机房环境"变化控制在最小"(§2.1);开放机房单机实验的温度噪声远大于此,拟合 Pearson 阈值(>0.75)可能达不到。
- **机龄数据仅 Table 3 级别粒度**(0.5–3.08 年),无机队级 age vs 失败率曲线——老化维度本文没有定量结论(那是 ASPLOS24 Vega 的领域)。
- **无温度以外的环境轴**:电压、频率、湿度等未测(相关工作只引文献);温度轴自己也只有 6/27 颗显著——复现"温度激发"预期命中率有限,需设计成"探索性协议"而非"确认性协议"。
- **深度实验与机队统计的断层**:机队层数字(3.61‱ 等)与深度实验层观察(19/8 分型、bitflip 分布)来自不同样本子集,两层之间无概率桥接(没有"计算型缺陷在全体坏 CPU 中占 70%±x%"这类机队级推断)——引用时分清层次。

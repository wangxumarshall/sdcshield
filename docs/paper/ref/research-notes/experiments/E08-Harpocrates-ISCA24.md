## 1. 研究问题与核心贡献(≤5 行)

研究问题:如何自动生成"短小、约束随机"的功能测试程序,使其对目标 CPU 微架构结构的故障检出能力最大化,并可部署在系统生命周期各阶段(制造后、在线、野外)。
核心贡献:
1. MuSeqGen —— 基于 IBM MicroProbe 的约束随机程序生成器+变异器,把 ISA 支持扩展到 x86-64(约 2,000 条 x86 指令变体,与 gem5 的 x86 支持程度对齐);
2. 硬件在环(hardware-model-in-the-loop)方法:用 gem5 微架构模拟器作为快速评分引擎,以硬件覆盖率为适应度函数迭代精炼测试程序,区别于 SiliFuzz 的硬件无关代理覆盖;
3. 闭环方法论:Generator + Mutator + Evaluator 三组件遗传算法式流水线,在 6 个关键硬件结构上证明:覆盖率提升 ⇒ 检出能力提升,且生成速率是 SiliFuzz 的 30 倍。

## 2. 实验方法(生成器架构、覆盖指标定义、评估闭环)

### 2.1 生成器架构:MuSeqGen(Fig. 9)

- 底座:MicroProbe(IBM 开源,公开版仅支持 POWER 与 RISC-V)。MicroProbe 分两大模块:
  - Architecture Module:一组配置文本文件,描述 ISA 全部细节(寄存器、指令、格式等),可选微架构细节(核组件、cache 配置、延迟);
  - Code Generation Module:编译器式的 pass 流水线(初始化、分支解析、内存操作数解析、寄存器分配等),pass 序列称为 policy,由 synthesizer 对象驱动,最终 lowered 为合法汇编。
- MuSeqGen 的扩展:
  - x86-64 ISA 支持:从结构化机器可读的 x86-64 ISA 参考文件(XML)出发,写解析器转换成 Architecture Module 配置文件;支持 ≈2,000 条 x86 指令变体;
  - 约束随机生成工具链:暴露所有可配置参数;
  - 变异引擎(Mutation Engine):试验过 k 点交叉与各种指令替换变体后,最终采用"指令替换"策略 —— 把序列中一条随机选中指令的**所有出现**替换为另一条随机指令(同一助记符不同操作数类型视为不同指令)。理由:(1) 可优化任意目标函数而无需单独调参;(2) 避免"过于显式"的变异策略导致程序平凡化、探索空间收窄或陷入局部最优;
  - Manager:脚本集合编排常见流程,例如"生成 10 个随机程序 → 每个随机变异 5 次 → 从共 25 个变异序列再生成"。
- x86-64 合法性约束(生成非崩溃、确定性汇编所必需,§V-B):
  - 寻址模式:实验中实现 RIP-relative 与 base+offset(框架可扩展任意寻址模式);
  - 隐式操作数:如 MUL 的部分结果隐式写入 RAX;若 RAX 同时被用作地址基址寄存器,MUL 后大概率段错误 —— 生成器必须建模隐式操作数;
  - 栈类指令:PUSH/POP 变体可能弹空栈崩溃;生成序列结束后需插入栈重对齐指令片段(x86-64 ABI 要求函数调用时栈 16 字节对齐);
  - 排除非确定性指令(与 SiliFuzz 作者观点一致),保证程序输出确定性。
- 程序结构(§V-D):
  - 程序 = 变长基本块经 CFG 连接;针对本文目标结构,确定**单基本块(线性指令序列)即足够**;所有分支解析到后继指令(taken 与 not-taken 等价),保证线性执行;
  - 寄存器分配:可配置策略(常数寄存器依赖距离、ISA 约束下随机分配、round-robin 等);本文设定为**最大化依赖距离**(maximize dependency distance),在高 ILP 与数据流传播之间取平衡;
  - 内存操作数:始终以 round-robin 方式解析,在 cache 大小的指定内存区域内、固定 stride 访问(例:32KB 区域、stride 32B → 可解析出 1K 个不同地址);
  - 立即数:全范围均匀采样;分支目标解析需精心设计以在操作数/内存/初始状态变化下保持控制流一致;
  - 包装(wrapper):极小 C 程序,把核心测试程序作为 main 函数中的内联汇编,负责寄存器/内存初始化与预热代码(保证所有核心指令在相似硬件状态下运行);输出 = **架构寄存器最终状态 + 被访问内存区域的签名(signature)**;gem5 指令隔离核心指令与初始化/输出计算代码,保证评估指标准确。

### 2.2 覆盖指标的形式化定义(§II-C/II-D)

- 硬件覆盖(generic 定义):绑定到特定 CPU 硬件结构(任意粒度:bit、寄存器、cache line、功能单元、译码器等)的任意目标(奖励)函数,须与功能程序对该结构的故障检出能力良好相关,且**测量必须快**以支撑迭代精炼。覆盖 = 程序"激活(敏化)故障 + 传播(可观测)"能力的一阶(快速)代理。
- **ACE(Architecturally Correct Execution)lifetime 分析 —— 用于位阵列结构(IRF、L1D、LSQ)的瞬态故障**:
  - 定义:逐周期计算对架构正确执行必要的 bit,标为 ACE;ACE lifetime 结果("vulnerability",0 到 1 / 0% 到 100%)即程序运行时该结构所有存储 bit 的硬件覆盖;
  - 计算:对每个存储 bit,ACE 周期数 / 总周期数;
  - Fig. 3 给出 cache bit 的 ACE 区间示例:write→read 与 read→read 区间为 ACE;fill、evict、un-ACE 区间不计;
  - 性质:ACE 是瞬态故障检出能力的**上界**(Mukherjee AVF 方法论,[16][48][49]);
  - 注意:ACE 不适合算术单元/门上的永久故障。
- **IBR(Input Bit Ratio)—— 用于功能单元的永久(门级 stuck-at)故障**:
  - 定义:程序执行期间进入某单元的总输入 bit 数 ÷ 理论最大输入 bit 数(假设该单元输入在程序执行的**每个周期**都被充分利用);
  - IBR 可 <1:64 位算术单元可能不是每周期都被使用;输入也不总是 64 位宽;IBR 只统计该单元实际被使用的周期内传入的有效输入 bit;
  - 性质:快速、类似 toggle-count 的测量;**不构成检出能力上界**,但量化单元被"锻炼"的程度;高 IBR + 低检出 ⇒ 软件层掩蔽(程序只把小部分功能单元结果传播到输出)。
- 两个指标与故障类型的对应关系(表):位阵列(IRF/L1D)→ 瞬态单 bit 翻转;功能单元(加法器/乘法器)→ 门级永久 stuck-at(瞬态故障在逻辑中被逻辑/时间掩蔽,[65],故功能单元不做瞬态注入)。

### 2.3 评估闭环(gem5 硬件在环,§III-B/§V/§VI)

- Step 0(Generator):MuSeqGen 并行产生初始随机程序种群(内在理解 ISA ⇒ 每个程序都是合法汇编);
- Step 1(Evaluator):程序**并行**在 gem5 中模拟,计算预定义评估指标(硬件覆盖)作为适应度分,排名;
- Step 2(Selection):top-K 晋级;
- Step 3(Mutator):按指令替换策略变异 top-K 产生下一代;回到 Step 1,循环直至指标收敛。
- 关键洞见:不能用 SFI(统计故障注入)直接做精炼内环 —— 单次 SFI 迭代需数小时,而覆盖指标单次程序执行即可测得(秒级甚至亚秒级);SFI 只用于**最终**检出能力评级(ground truth)。
- SFI(§II-E,GeFIN):微架构级注入、软件级观察([45][51]–[54]);结果分类:SDC(传播到程序输出且无可观测指示)/ 应用或系统崩溃 / 硬件或软件层掩蔽;CPU 保护机制(奇偶校验、ECC)在注入建模中考虑:无保护 cache 单 bit 翻转 → Masked/SDC/Crash;SECDED cache → Masked(Corrected)。
- 检出能力定义:注入 N 个故障、程序检出 n 个,检出能力 = n/N。

## 3. 实验配置(模拟器/硬件、基准、参数)

- 评估引擎:gem5(定制扩展:ACE lifetime 分析 + IBR 度量 + 多故障类型注入);故障注入用 GeFIN(gem5-based injector,[40]),重要扩展:向 CPU 功能单元的**门级模型**注入故障;gem5 版本 v22.0.0.2(§VI-D 提及)。
- CPU 模型:乱序核,微架构参数与容量基于公开的商用 x86 CPU 数据(原文未给出具体参数表)。
- 故障注入能力:瞬态/间歇/永久,可注入 **>70 个**不同硬件结构(cache、寄存器堆、队列、缓冲、分支预测器、算术单元等)。
- 6 个目标结构(a–f):(a) 物理整数寄存器堆 IRF;(b) L1 数据缓存 L1D;(c) 整数加法器;(d) 整数乘法器;(e) SSE 浮点加法器;(f) SSE 浮点乘法器。前 4 个为与 SiliFuzz/OpenDCDiag/MiBench 公平对比而选(这些结构可被通用负载合理利用);两个 SSE FP 单元因超大规模厂商报告明确指出 FP 单元(标量与向量)是 SDC 高发源([3] SOSP23)。
- 注入模型:
  - 位阵列(IRF、L1D):瞬态故障,bit 与周期均匀随机分布;每次执行单 bit 在随机周期翻转;
  - 功能单元(整数/SSE FP 加法器与乘法器):门级永久故障;所有功能单元门级建模,均匀采样一组随机门,每次迭代选一个门注入 stuck-at-0 或 stuck-at-1,持续到执行结束。
- 对比基线:
  - **SiliFuzz**:对 Unicorn x86 模拟器 fuzz(全部核,40 分钟)得 635,587 个测试输入;5 分钟筛选出非崩溃且确定性的程序,保留约 1/3 = 173,731 个;多个 snapshot(每个最多 100 字节二进制代码)聚合为单个 10K 指令测试(与方法论典型测试程序尺寸一致);
  - **OpenDCDiag**:逐个测试评估,单次完整执行;输入尺寸配置为**不超过 1 亿(100M)周期**;开源测试含压缩、密码学、矩阵乘法、SVD;
  - **MiBench**:12 个通用基准(广泛用于同类研究 [43][45][51]–[53][61]–[64])。
- 宿主机:dual-socket AMD EPYC 7402 24 核(96 超线程),128GB DDR4。
- 种群/迭代参数(§VI-B):
  - IRF:程序 10K 指令;每迭代评估 96 个程序(= 机器最大硬件线程数,充分利用并行),保留 top-16,每个变异 6 次 → 96 个后代;共迭代 10,000 次,图每 1,000 次迭代显示 top-16 覆盖;
  - L1D:程序 30K 指令;内存引用在 32KB 区域内 stride 8B 顺序解析(32KB = 数据 cache 精确容量);每 100 次迭代采样 top-16;
  - 整数加法器:程序 5K 指令;每迭代 32 个程序,保留 top-8,每个变异 4 次;每 100 次迭代采样;
  - 整数乘法器:与加法器相同配置;
  - SSE FP 加/乘法器:与前述功能单元类似配置。

## 4. 实验步骤(可操作流程,编号)

1. **搭建 gem5+GeFIN 评估引擎**:gem5(v22.x)OoO 核,参数对齐商用 x86 CPU 公开数据;扩展 ACE lifetime 逐 bit 逐周期统计、IBR 门级输入统计、故障注入(位阵列瞬态单 bit 翻转;FU 门级 stuck-at)。
2. **构建 MuSeqGen 生成器**:MicroProbe 架构模块导入 x86-64 ISA 配置(≈2,000 指令变体);配置 pass/policy(单基本块线性序列、分支全落下一步、寄存器分配最大化依赖距离、内存 round-robin 固定 stride、立即数全范围均匀采样、C wrapper 内联汇编 + 寄存器/内存初始化 + 输出签名)。
3. **跑基线**:MiBench 12 个、OpenDCDiag 全部开源测试(≤100M 周期)、SiliFuzz snapshot 聚合的 10K 指令测试,在 gem5 中测覆盖率(ACE/IBR)与 SFI 检出率(Fig. 4/5/6)。
4. **初始化种群**:MuSeqGen 并行生成随机程序(每结构按上述参数:10K/30K/5K 指令)。
5. **评估-选择-变异循环**:gem5 并行模拟算覆盖率适应度 → top-K(16/8)晋级 → 指令替换变异(6/4 次)→ 下一代;迭代至收敛(FU ≈1,000 次;L1D ≈2,000 次;IRF ≈5,000 次)。
6. **SFI 终评**:对每个结构的最优程序做统计故障注入(瞬态/门级永久),得检出能力 n/N;同时记录达到 99% 检出所需周期数。
7. **对照分析**:覆盖率 vs 检出率散点(Fig. 10)验证正相关性;与基线最大/平均检出对比(Fig. 11);生成吞吐对比(Table I vs SiliFuzz 45 分钟流程)。

## 5. 实验数据(关键数值 + 图表号)

### 5.1 动机数据(Fig. 1)
- 超大规模厂商披露 DPPM:2021-01 [1] ≈1,000 DPPM("数十万台机器中数百台 CPU 检出 SDC");2021-06 [2] 略低于 1,000("数千台机器中几个 mercurial core");2023-10 [3] = 361 DPPM("3.61 CPU / 10,000")。可接受值:安全关键(车规)<10 DPPM;云/HPC 数百 DPPM。

### 5.2 基线覆盖率/检出率(§III-C;Fig. 4/5/6)
- **IRF(Fig. 4,瞬态)**:三个框架绝大多数程序检出 <5%;MiBench 与 SiliFuzz 少数离群点勉强过 5%。覆盖率恒高于检出率(ACE 上界性质);检测距上界差距大 ⇒ 软件掩蔽显著。
- **L1D(Fig. 4,瞬态)**:三框架检出显著高于 IRF;单个 OpenDCDiag 程序 >80%。
- **整数加法器(Fig. 5,门级永久)**:三组负载平均检出 ≈80%;MiBench 与 OpenDCDiag 各有一个离群程序分别达 99% 与 98%。
- **整数乘法器(Fig. 5)**:平均检出 MiBench 53%、SiliFuzz 70%、OpenDCDiag 37%;最高为 SiliFuzz 生成负载 87%;MiBench 与 OpenDCDiag 最大值分别为 67% 与 58%。
- **SSE FP 加/乘法器(Fig. 6)**:多数负载不用 SSE ⇒ 仅 4 个 MiBench 与一半 OpenDCDiag 基准非零检出;OpenDCDiag 最佳:SSE FP 加法器 98.5%、SSE FP 乘法器 58.2%(FP-heavy 负载:MxM、SVD 等)。
- IBR 高 + 检出低的大量实例 ⇒ 软件层掩蔽(功能单元结果只有小部分传播到输出)。

### 5.3 生成吞吐对比(§VI-A;Table I)
- SiliFuzz(作者实测):Unicorn 全核 fuzz 40 分钟 → 635,587 输入;5 分钟筛选 → 173,731 个可运行确定性程序(保留 1/3);平均每程序 18.6 条指令;45 分钟共 3,230,528 条可运行指令 ≈ **1,200 指令/秒**。
- Harpocrates:单次变异/生成/评估循环 13.35 秒处理 96 个 5K 指令程序 = 480,000 指令 ≈ **36,000 可运行指令/秒**,为 SiliFuzz 的 **30×**。
- Table I 单循环耗时分解:Mutation 0.51s / Generation 9.18s / Compilation 1.12s / Evaluation 2.54s / **Total 13.35s**。
- 若用 SFI 直接做精炼内环:单次迭代需数小时(vs 13.35 秒)。

### 5.4 收敛与覆盖(§VI-B;Fig. 10)
- IRF:10,000 次迭代,≈5,000 次收敛;覆盖率达其他框架最佳测试(Fig. 4 上图)的 **>3×**;
- L1D:≈2,000 次迭代收敛;最大覆盖 **95%**;因 cache 感知约束,首代即高达 ≈77%;
- 整数加法器:略超 1,000 次迭代收敛;饱和于 ≈**10% IBR**;全流程 <2 小时;
- 整数乘法器:1,000 次迭代收敛;饱和于 **6% IBR**;两个整数 FU 的覆盖均为其他框架最佳程序的 **2×**(Fig. 10 中图 vs Fig. 5);
- SSE FP 加法器:5,000 次迭代收敛,饱和 7% IBR;但 SFI 显示检出在 step 500 即达峰、稳定在略低于 100%(图截断到 step 1,100);
- SSE FP 乘法器:5,000 次迭代,饱和 5% IBR;检出 step 600 达峰(截断到 1,100);SSE FP 两单元覆盖为其他框架的 **>10×**;
- 全部结构:覆盖提升 ⇒ 检出提升(Fig. 10 核心观察,验证方法论根基假设)。
- 收敛难度:FU ≈1,000 循环;L1D >2,000;IRF ≈5,000 —— 位阵列(瞬态)本质上比功能单元(永久)更难。

### 5.5 最终检出率对比(§VI-C;Fig. 11)
- IRF:Harpocrates 检出 ≈其他框架的 **10×**(瞬态故障、寄存器分配/释放极频繁的结构);
- L1D:OpenDCDiag 最佳 ≈80%;Harpocrates 逼近 **90%**;
- 整数加法器:各框架最佳程序均近全检出(SiliFuzz 略落后),但其他框架**平均**检出差;
- 整数乘法器:Harpocrates 近 **100%**;
- SSE FP 加法器:Harpocrates **99.8%**(数量级更少周期);
- SSE FP 乘法器:非 Harpocrates 最高仅 58.2%(OpenDCDiag 单程序);Harpocrates **99.7%**;
- Harpocrates 是唯一在**所有**功能单元上近全检出的框架。
- 检出速度:MiBench 单程序在整数加法器追平 99% 检出但需 **>1,100 万周期**;Harpocrates 仅 **50,000 周期**(≈**220×** 快);乘法器同理;运行时间相当时,SiliFuzz 最佳测试检出 86.6%,Harpocrates **99.5%**。
- 覆盖-检出间隙:Harpocrates 程序 ACE 覆盖与检出间隙极小(软件掩蔽可忽略);IBR 与检出强相关 ⇒ 程序把功能单元结果传播到输出。

### 5.6 意外发现(§VI-D)
- Harpocrates 生成的程序暴露 gem5 v22.0.0.2 内部断言错误:RCR 指令模拟 bug(旋转量等于被旋转寄存器尺寸的角落案例),后续版本已修复(commit 1dd30723)。

## 6. 实验结论(编号列出)

1. 硬件在环(gem5 覆盖反馈)迭代精炼可行且高效:13.35s/代,30× 于 SiliFuzz 吞吐;SFI 内环不可行(小时级/迭代)。
2. 覆盖代理与检出能力正相关:ACE(位阵列瞬态)与 IBR(FU 永久)是经 SFI 验证的有效适应度函数;ACE 是上界,Harpocrates 程序逼近上界(软件掩蔽极小)。
3. 位阵列瞬态故障(IRF/L1D)远难于功能单元永久故障:收敛迭代 5,000/2,000 vs 1,000;现成框架(MiBench/OpenDCDiag/SiliFuzz)IRF 检出普遍 <5%。
4. Harpocrates 在全部 6 个结构上达到或接近最高检出:IRF ≈10×基线、L1D ≈90%、整数乘法器近 100%、SSE FP 加/乘 99.8%/99.7%。
5. 检出速度优势巨大:99% 检出 50,000 周期 vs MiBench 11M 周期(220×)。
6. 生成器可暴露模拟器自身 bug(gem5 RCR)—— 生成测试的附带价值。
7. 方法论通用:任意 gem5 支持的 ISA(x86/Arm/RISC-V)、>70 个可注入结构、任意覆盖度量、任意故障模型可组合。

## 7. 复现要点(ARM64 复现最小版本)

### 7.1 可直接复用
- **评估闭环骨架**:Generator → gem5 评分(覆盖适应度)→ top-K 选择 → 指令替换变异 → 迭代至收敛。此闭环与 ISA 无关,SDCShield 可直接借用其"覆盖率反馈驱动演化"范式。
- **gem5**:原生支持 ARM ISA 与 O3CPU(公开 Neoverse/N1 类配置可直接用),是 Harpocrates 明确列出的可替换维度("gem5 supports x86, Arm and RISC-V ISAs")。
- **GeFIN**(gem5 微架构级故障注入器,开源):瞬态单 bit 翻转注入 ARM O3 的物理寄存器堆/L1D 在原则上直接可用;多次可靠性研究([41]–[47])在 gem5-ARM 上使用过同类注入。
- **ACE/IBR 指标定义**:形式化定义 ISA 无关;ACE 逐 bit 逐周期统计、IBR = 实际输入 bit / 理论最大输入 bit,可在 gem5-ARM 上以 probe/listener 实现。
- **SFI 评估协议**:位阵列瞬态(随机 bit × 随机周期)、FU 门级 stuck-at(随机门、持续到结束)、结果三分(SDC/Crash/Masked)、检出 = n/N。
- **基线**:OpenDCDiag = SDCShield 直系上游(现成);MiBench(embecosm/mibench,开源);SiliFuzz(google/silifuzz,公开仓库已支持 aarch64)。
- **变异策略**:"一条指令的全部出现 → 随机替换"的粗粒度变异 + top-K(16/8)精英保留 + 每代 6/4 变异体 —— 参数可直接照搬。
- **C wrapper 模式**:内联汇编 + 寄存器/内存初始化 + 预热 + 输出(架构寄存器终态 + 内存签名)—— 与 SDCShield 现有测试框架(TEST_LOOP/memcmp_or_fail)高度兼容。

### 7.2 需替代/不可行
- **MuSeqGen 本体不开源**:x86-64 扩展(≈2,000 指令变体)与变异引擎是论文私有实现;MicroProbe 公开版仅 POWER/RISC-V,**无 ARM 支持** → ARM64 复现需自建生成器(最小版本:基于 SDCShield 现有 per-arch 指令表 + 汇编器随机发射,约束:单基本块、XZR/SP 不可写、SVE 谓词寄存器合法性、NEON/SVE 编码合法性)。
- **x86 特有约束不可移植**:RIP-relative 寻址、RAX 隐式操作数、PUSH/POP、16 字节栈对齐片段 → ARM64 对应物:SP 16 字节对齐、X31(XZR)、链接寄存器 LR 被隐式写(BL)、SIMD&FP 寄存器 v0–v31、SVE ZA/谓词状态(SME)。
- **SSE FP 加/乘法器目标结构**:ARM64 无 SSE → 对应 NEON FADD/FMUL(vector)流水线或 SVE FADD/FMUL;gem5-ARM 对 SVE 的 O3 流水线功能单元建模有限(SVE 支持不完整),**门级 FU 建模基本不可行**。
- **门级 stuck-at 注入(功能单元)**:GeFIN 的门级 FU 模型是论文的重要扩展,公开 GeFIN 版本以微架构级为主;ARM64 上复现"功能单元永久故障"更现实的替代是**微架构级功能单元输出翻转(永久)**,需在复现报告中声明偏差。
- **商用 x86 CPU 参数对齐的 OoO 配置**:原文未给出参数表;ARM64 复现应改用公开 Neoverse V1/N2 参数并声明。
- **>70 结构注入**:Micro'26 版说 >50 目标(两文数字不一致);实际可注入结构清单未公开,复现时以 GeFIN 开源版实际支持为准。

## 9. 局限与坑

1. **全部实验在 gem5 仿真中**(注入与评级均是),无任何真机检出数据:gem5 OoO 模型与商用 CPU 的保真度差距直接决定结论外推的可靠性;真实缺陷(边际缺陷、老化)的行为未必与瞬态 bit 翻转/门级 stuck-at 模型一致。
2. **FU 检出率数字的门级模型依赖**:99%+ 检出建立在"随机采样门 + stuck-at 持续到执行结束"的永久故障模型上;论文自己承认(Micro'26 前缀实验讨论)更真实的 FU 故障模型(间歇/边际、路径延迟)可能需要更长序列 —— 高检出率对永久故障是"容易模式"。
3. **6 个结构的覆盖指标饱和值差异大**(IRF 覆盖 3× 但绝对值、L1D 95%、FU 的 IBR 仅 5–10%):IBR 绝对值低且不是上界,跨结构比较覆盖数字无意义,只能比检出率。
4. **SiliFuzz 基线的测量口径**:Harpocrates 自己跑的 SiliFuzz(40 分钟 Unicorn fuzz、聚合 10K 指令)≠ Google 生产环境 SiliFuzz;1,200 指令/s 是论文作者环境下的数字。
5. **OpenDCDiag 基线"单次完整执行 ≤100M 周期"**:输入裁剪会改变其负载特征,与生产用法不同。
6. **x86-64 生成器的合法性工程量大**(隐式操作数、栈对齐、非确定性指令排除),论文只给代表性子集;复现者会在每个 ISA 的角落案例上反复踩坑(论文的 gem5 RCR bug 即例证)。
7. **单基本块线性程序 + 全部分支落到的设计**:对分支预测器、乱序窗口深处结构(ROB、LSQ —— ISCA'24 未做)覆盖有限;LSQ 要到 Micro'26 才补上。
8. **未给出**:gem5 OoO 配置参数表、SFI 注入样本量 N、统计置信区间、每结构程序的实际汇编样例、变异收敛的方差 —— 复现时这些都要自定并声明。
9. **未测间歇性故障**:基础设施声称支持,但 ISCA'24 无间歇故障实验数据。
